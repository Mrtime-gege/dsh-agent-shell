## 0.3.0 — 人机双接管 + 双域输入（vault/macros）+ steps/expect + 闲置默认永久（2026-09-17）

功能清单与用法见 [CHANGELOG](CHANGELOG.md) 与 README「人机双接管」教程；这里只记**根因与验证**
（为什么这么设计、哪里踩过坑、怎么确认修好）。

### 闲置默认翻转为什么动了三处

维护者定的新语义："默认永久不关，显式指定时长才启用，不指定或 -1 = 不启用"。落地时发现
**默认值有两个源**：z schema 的 `.default()` 与 `resolveConfig` 的代码级回退
（`source.idleClose !== false` —— 除显式 false 全当 true）。只改 schema 时实机依旧"全局开"，
因为宿主没走 settings 服务的解析路径时吃的是代码级回退。教训：**翻转默认必须两个源一起翻**，
且用"配置里没有该键"的 harness 实测（edge hFeat 无 idleClose 配置 → 断言 `idle=永久(未指定)`）。

### 审计链"断链于第 4 条"：一个潜伏两个版本的规范化 bug

现象：edge E 流 CLI 复验 exit=1，26 条记录只有 3 条过验。手工 dump 发现 13 条记录**全部带
hash**、prevHash 链接正确 —— 断的是**摘要复算**：写入方对 `idleMinutes: undefined` 的记录做
`canonicalize`（`stableValue` 把 undefined 归一成 **null**，键保留），落盘却走
`JSON.stringify`（undefined 键**直接消失**）；校验方 parse 回来的对象没有这个键，规范化结果
少一个 `"idleMinutes":null` → 摘要必然失配 → 链从该条起全判"篡改"。0.2.x 没炸只是因为
从未有调用方传过 undefined 字段；0.3.0 的"默认永久"（`idleMinutes: undefined`）第一次踩中。
修复：`canonicalize` 与 `stableValue` 的对象分支都**丢弃 undefined 键**（与 JSON 语义同口径；
数组元素里的 undefined 仍按 JSON 语义成 null）。回归锁：`sealRecord(带 undefined) → JSON 往返
→ hashRecord 一致 + verifyChain ok + canonicalize({a:1,b:undefined})==='{"a":1}'` 三条纯函数断言。

### vault 的三条安全决定（与一条诚实边界）

1. **打码表在发送前登记**（不是发送成功后）：值一进 pane，下一次读屏就可能带回来；等异步的
   oneShot 消耗再登记会漏一帧。"烧"（删键）才放在发送成功后 —— 注入失败不该烧掉用户的键。
2. **护栏扫展开后文本，但拒绝消息/审计只用原文**：宏可能展开出 `rm -rf /`（必须拦），而展开
   文本可能含 vault 值（拒绝消息里回显命中行 = 泄密）——所以命中时 candidate 显示为占位说明。
3. **oneShot 重复引用 = 违规不烧**：同一条命令里 `{{v:k}}` 出现两次还想"用两次再烧一次"是
   绕过一次性的形状，`vaultConsumeNow` 纯函数判定并记 `consume-violation` 事件。
4. **诚实边界**：`output/` 留痕是 tmux pipe-pane 原始字节流，绕过一切 JS 路径 —— vault 值进过
   pane 就在留痕文件里。vault 防的是 AI 上下文/审计文本/工具输出/面板显示四个面，**不防本机
   磁盘**（同权限进程本来就能读）。写进 SECURITY 第 10 节与 README 教程，不假装银弹。

### 多行文本的隐性 Enter（paste 通道）

旧 `driver.send` 把含 `\n` 的文本整块 `send-keys -l` —— 每个换行都是隐性 Enter，多行内容
= 逐行立即执行（危险默认）。0.3.0 多行一律走 `load-buffer + paste-buffer -p + delete-buffer`
（临时文件 0600 即删）：readline 类 shell 整块接收，提交与否由宏 `submit` 语义决定
（`macroSubmitWantsEnter`：贴块尾部有未提交行才补 Enter，宏自带结尾换行则不补——防空提交）。
不支持 bracketed-paste 的 TUI 会把整块当逐行输入 —— 已写入宏的文档边界。

### steps/expect 为什么能这么便宜

expect 的全部原语（`parseWaitFor` 条件解析、`diffSince` 增量、`stripCommandEcho` 回显剥离、
`portOpen`/`existsSync`）都是 0.2.3 造好且有单测的；steps 只是把 shell_run 的"发送→等待"
循环体参数化成数组，失败路径复用 `summarizeFailure`+`tailOf` 回现场。新增代码集中在
`runSteps` 一个函数里，语义与单步 shell_run 完全一致（同护栏、同审计、同让位规则）。

### 闲置自动关闭（设置开关 + 会话级时长，全工具统一分钟）
- 新设置 `idleClose`（默认开）+ `idleCloseMinutes`（默认 60，1–1440，热更）；`shell_open
  idleMinutes` 创建时定值（0=永不），`shell_manage action=idle` 随时改。扫描 30s 一趟 + 启动
  8s 首趟；判定抽成 pure `idleClosable`（缺 lastUsedAt 一律不关、skip 豁免）；关闭走统一 close
  路径并记 `event:close reason:idle-timeout`。**根因级补丁（实机）**：重启收养原依赖 ready 时
  的 alive 列表，若那一刻 tmux 尚不可见（catch 吞掉），第一趟扫描会把"刚活过重启"的会话当长期
  闲置收掉——实机 23:58 重启、00:07 收掉 10 分钟闲置的测试会话即此形态。修法：每次启动挂
  `state.adoptionPending`，第一趟扫描对存活会话补拨一次 lastUsedAt（一趟制）。
- 验证：真机 1 分钟闲置会话 76s 走完"扫描→关闭→快照"；重启后验证会话存活（新 harness pid
  收养无丢失）。

### AI 精准四件套（用户点选 1+2+4+5）
- **① `shell_run { waitFor }`** 条件等待：`match:<正则>` / `file:<路径>` / `port:<回环端口>`
  （`waitTimeout` 兜底，设了就不等空闲、不取退出码）。解析抽 pure `parseWaitFor`，非法立即 REFUSED。
- **② 失败摘要**：pure `summarizeFailure` 挑错误行（error/failed/No such file/Traceback…）；
  提示符（框线 `┌└╭╰`、`㉿`、裸 `$`/`#`）过滤——实测不认框线会把提示符当摘要。
- **③ `retry:'last-failed'|'last'`** 重跑：命令完整原文入台账（`state.lastRuns`，≤4000 字符）；
  最近一条不是失败时明确说明而非默默重跑。
- **④ `shell_manage action=doctor`** 会话自检（pure `doctorAdvice`）：fg/无活动秒/缓冲占用/
  idle/留痕，给可执行建议（读 `#{session_activity}`）。

### `until`/`waitFor match:` 增量语义钉死（实机长任务验证发现并修复）
- **根因一**：原 `sincePreview` "底部逐行比对"，最后一行一变（任何流式输出/进度刷新）差异段
  退化成整屏 → **等待词出现在自己发的命令回显里会 0.0s 假成功**。
- **根因二**（第一版修复引入、被真帧打回）：基线改"发送后/idle 循环后"会吞掉短命令的全部输出；
  且基线提示符被输入改写后，旧帧在**新帧顶部**不复存在、唯一完整副本是**底部新提示符**——
  取"最后一次出现"会误判"旧帧还在屏底"而吞掉真输出（edge `waitFor match` 超时实证）。
- **终版**：`pure.diffSince` 整行对齐：①整帧尾部块取**第一次**出现且要求块后留有新内容；
  ②不中则去掉基线"光标行"再对齐；③旧帧复现到屏底=无新内容；④旧帧滚出=全屏皆新。
  `waitFor match` 基线=**发送前** + `pure.stripCommandEcho`（去空白拼接、前缀渐进，兼容折行劈词
  与 `└─$ ` 提示符前缀）；`until match` 基线=开始等待那一刻。
- 验证：pure 138→**160**（diffSince 11 + stripCommandEcho 9）；smoke 1b（回显含等待词、输出
  没有 → 必须超时）；edge `waitFor file/match`、`until` 旧词/新词用例；实机三路并行
  `until=match`（45/60/75s 错峰标记全部 reached，总耗时≈36s 证真并行）与回显反例超时。

### 结构化退出码（A）+ 最近结果（B）
- `shell_run` 默认包一层安全取码（pure `shouldWrapExit`/`wrapExitCommand`/`parseExitFromTail`）：
  多行/heredoc/后台/交互白名单（vim/ssh/sudo/python/**bash/sh**…）自动跳过；护栏与审计按**原始
  命令**判定；返回 `✅/❌ exit N + 耗时 + 尾部`；失败留 `lastRuns`，`shell_state` 每会话
  `last=` 显示 5 分钟。**已知边界（实机记录）**：以 shell 名开头的命令不取码（保守白名单）；
  前台判定按进程名——`bash -c` 循环可能瞬时被采样为"空闲"，等长任务请用 `waitFor`/`until`，
  且注意**两次工具调用之间有秒级延迟**：输出已滚过的再 `until=match` 会被正确判为旧文本，
  等刚发命令的结果要用 `waitFor`（与发送同一次调用）。

## 0.2.2 — AI 批量发送（工具层）+ 互斥升级「一切修改」+ shell_wait 增量匹配 + 授权菜单按活跃排序

（本轮为**功能增量**，全部经 test-client 388 / test-edge 全料验证，UI 改动已真机走查。）

1. **AI 批量发送（工具层）**：`shell_send` / `shell_run` 的 `session` 接受逗号列表或 `*`
   （如 `"dsh-a,dsh-b"` / `"*"`）—— 一次把同一命令发到多个/全部 shell，按列表顺序逐个执行。
   **这是给 AI 用的**：WebUI 输入框只服务于"人操作单根终端"（它是允许操作，不是好用），不做批量。
   ⚠ 0.2.2 早期草稿误把"批处理"做成面板「发送到全部」按钮，用户澄清后**已撤销**（按钮、图标、
   broadcastAll、相应测试断言全部移除），文档同步改为工具层表述。
2. **人机互斥升级为「一切修改」**：解锁中的 shell，AI 的**发送、改名、改尺寸、关闭（含 reap）**
   全部让路 —— `sendKeys`/`shell_run`/`shell_manage`（rename/resize/close/reap 四动作）逐一
   检查 `userBusyRefusal`；被拦返回统一文案（"用户正在操作终端 X（面板已解锁）：AI 写操作已暂停…"）
   并记 `guard:'user-busy'` 审计；**面板自己的操作（/keys、/kill、/rename、/resize）不拦**（那是人）。
   只读（`shell_read`/`shell_state`/`shell_audit`、`/list`）不受影响。
3. **人机互斥跨面板可见**：`/list` 每个会话带 `userBusy: true/false`；`shell_state` 对正在被
   人操作的会话标注 `⚠用户正在操作(面板已解锁)`。之前只有"撞到拒绝才知道"，现在
   **list 一眼可见** —— AI 决定要不要写之前先看状态，不会盲试。
4. **shell_wait `match:` 改为增量匹配**：原来对**整屏 tail** 做正则，等待开始前屏上已有的旧词
   （比如上一条命令的输出）会让 match **立刻假成功**；现在只对**等待开始后新出现的输出**匹配
   （复用 `sincePreview` 增量快照，与 `shell_read since` 同一套机制）。超时保留：默认 30s、
   可传 `timeout` 覆盖 —— **不会无限等待**（工具文档本就写明）。
   验证：edge 新增两断言 —— 屏上旧词 `OLD_MARK_777` → `timeout`（不假成功）；等待期间新出现的
   `FRESH_MARK_888`（`sleep 1; echo` 延迟产生）→ `reached`。
5. **授权菜单按「最近活跃」排序+相对时间**：`/actors` 排序键从 `createdAt`（创建时间）改为
   **活跃时间**（标题快照 `updatedAt`，无则退回 `createdAt`）降序 —— 最近用过的对话排最前；
   每项新增 `created`/`updated` 字段；面板每项显示相对时间（`刚刚 / N 分钟前 / … / N 天前`，
   纯函数 `timeAgoText`，测试覆盖边界：NaN/非数值 → 空串）。测试桩 `updatedAt` 故意与
   `createdAt` 顺序相反，断言排序确实按活跃而不是按创建。

## 0.2.0 — 工具面 v2 重构 + 稳定 id 会话身份（破坏性）

### 身份重构：寻址与显示解耦（用户点名的隐患）

**隐患**：此前会话以**名字**寻址，而名字用户可随时改 —— 改名后按旧名操作全部失联
（`can't find session`），且归属/审计/留痕的主键跟着飘。用户问"定位靠名字还是 id"，
答案必须是：**靠 id，名字只用于显示**。

**落地**：
- tmux 会话名 = **生成的内部 id**（`dsh-<8位随机>`），创建后**永不改名** —— 一切寻址
  （send/read/run/kill/审计/归属/留痕）都以它为键；
- 用户给的名字 / 后续改名 = **label**（`set-option -t <id> @dsh-label`），只出现在展示
  与 `shell_state` / `/list` 的 `label` 字段；改名不再搬 owners、不再重写审计主键；
- `sanitizeName` 仍用于 label 的规范化；`/rename` 与 `shell_manage rename` 一律只改 label
  并返回"id 不变、label 已改"。

### 工具面 v2（11 → 9 个原子工具，全部新契约）

原则（每条都来自本会话实测的模型摩擦）：
1. **选择器是原语**：`session` = 单 id / 逗号分隔 / `mine`（本对话建的）/ `*`（全部）；
2. **等待内置**：`shell_run` 发命令→等前台回空闲→只回"新输出"（替代 send+sleep+read）；
   `shell_wait` 做条件等待（idle / fg:<cmd> / match:<re>），模型不再盲 sleep；
3. **结果分帧聚焦**：按会话分帧（`[id] …`），`shell_read mode:"since"` 只给增量
   （底层是控制模式的 %output 语义 + 快照对比）；
4. **守卫裁决是返回值**：每次发送都显式带回 allowed/refused；`shell_check` 可**预检**
   不发，杜绝"发出→被拒→重试"回合；
5. **能力映射同步**（consent.js）：`run/send/manage`=full，`read/wait/check/state/audit`=read。

**破坏性**：旧工具名（shell_history/list/resize/close/rename/consent/diagnose）全部移除；
参数与新语义见工具 description。**面板无 UI 改动**（仍按 id 寻址）。

### 提速：tmux control-mode 长驻客户端 —— "复用同一个进程"落地

**目标**：把"每个操作 spawn 一个 tmux 客户端、经 subprocess 服务实测 ~100ms 固定开销"变成
"往一个长驻进程的管道写一行 ≈1ms"。这是用户点名的"现阶段最优解"，也是之前两轮（合并调用、
自适应轮询）之后剩下的大头 —— /screen 合并后实测仍 ~140ms，其中 ~100ms 是**每次 spawn 都绕不开**
的 systemd scope 建销（D-Bus + systemctl 确认；裸 tmux capture-pane 只要 4.5ms，读
dsh-subprocess-local 源码确认了这条链路）。

**方案**：`subprocess.spawn` 一个长驻 `tmux -C`（**不带 attach**），命令走 stdin（按命令串行化、
回复按 `%begin/%end` 分帧配对）、窗格输出以 `%output` 通知即时到达。它照样是 subprocess 服务管理的
scope 子进程：dispose / 超时 / 输出上界一条不丢。失败自动退避 60 秒并**回退一次性路径**，不会更糟。
`/screen`、`/list`、守卫扫屏、`foregroundOf`、`send-keys`（面板逐键）都优先走它。

**实现过程中实测出来的六条 tmux 3.6b 行为**（每条都踩过坑，将来改这块必读）：

1. **`tmux -C` 会给客户端自建默认会话**（"1"、"2"…，每次连接 +1，`%session-changed $1 1`
   可见）。它**不能杀**：那是客户端唯一的"当前会话"，杀了客户端会连它一起 `%exit`，
   `%output` 中继随之归零（实测）。
2. **`%output` 只发给"客户端 attach 的窗格"**。最早"attach 到隐藏会话还能收别的会话输出"的
   验证是**错的**（那 5 条收据实际来自隐藏会话自己）。所以不能 attach —— 用无 attach + 幻影
   留着但**从列表过滤**（纯数字名，插件会话都有 dsh- 前缀，判据可靠）。真实会话的
   `session_attached` 保持 0（`-C attach` 会置 1，污染面板的"有人接入"）。
3. **接入噪声**：连接瞬间有一组无输出的 `%begin/%end`（外加 `%window-add` 等通知），会偷走
   第一条命令的 waiter → 首条命令拿到空 payload。解决：spawn 后等"无 waiter 的 %end"（接入
   噪声收完）再放行命令，2 秒收不到也放行（老 tmux）。
4. **`;` 串联在 control mode 里每条命令各自成帧**（display-message 一帧、capture-pane 再一帧）。
   一次只等一帧会提前返回（屏幕=1 行），第二帧的 %end 还会**偷走下一条命令的 waiter、并把
   %output 吞进残留帧** —— 四条症状同源。改成分开两条命令（各 ~1ms 管道往返，依然零 spawn）。
5. **`%output` 判定必须无条件先于帧累积**：`send-keys Enter` 的帧还没关、命令输出就先以
   %output 到达（与 %end 竞态），先查 frame 会把它吞进命令帧 —— 监听者收不到任何变更通知。
6. **async 函数里光 `await` 是语句**：`command()` 的 task 漏了 `return await`，导致首条命令
   一直返回 undefined —— 低级错误，但症状（空 payload）和 3 撞得一模一样，浪费了最多排查时间。

**测试基建一并修了两个老 bug**（都不是用户报的，但都让"测试可信"破产）：

- **kit 的假 subprocess 把 stdin 设成 'ignore'、handle 上根本没有 stdin/stdout** —— control
  模式在测试里永远起不来（静默回退一次性路径，功能恰好像"通过"）。补上真实管道与
  `terminate()`。
- **kit 的 settings 源不含 socket**，而插件 schema 里 socket 默认是 **dsh-agent（生产名）**：
  带 `__withSettings` 的测试插件实际跑在**生产服务端**上（实测踩过：一次崩溃把会话留在了生产
  tmux 服务端，后续测试立刻撞上 maxSessions 上限；这也解释了"为什么修完某些 bug 后测试反而
  开始崩"）。`settingsSource = () => ({ socket, ...config })` 一行修复。

**怎么验证的**：新增 7.77 节，全部通过 —— control 客户端常驻/可达（`ready=true`）；meta+屏幕
两次命令分别配对（行数 = paneHeight，`trim:false` 语义与一次性路径一致）；`session_attached=0`
不被污染；幻影纯数字名从列表消失；`send-keys` 引号/`$` 原样送达（C-u 清行收尾，不成命令的字符
不能用 Enter 提交，会把 bash 带进 PS2）；`%output` 通知到达；前台探测报 sleep；服务端消失后

**代价与边界**：control 客户端与 tmux 服务端之间是**一长活** —— 服务端被杀会带走客户端

### 修复：面板改名"不生效"（一个症状，三个独立原因 + 两个连带缺陷）

**症状**（用户报）：在 WebUI 里改 shell 的名字，改完不生效。

**复现** —— 直接对线上 `/plugins/shell/rename` 打请求，三种输入三种结果：

| 输入 | 结果 |
|---|---|
| `lat2` | ✅ `dsh-lat2` |
| `测试` | ❌ HTTP 400，而且报错是英文的：`newName must contain at least one letter, digit, underscore or dash` |
| `测试abc` | ⚠️ **HTTP 200「成功」，名字却变成 `dsh-abc`** —— 中文被静默吃掉 |

**三个独立原因**（少修一个，用户还是会说"不生效"）：

1. **`sanitizeName` 只认 ASCII**：`[^A-Za-z0-9_-]` 一律折成 `-`，再删首尾 `-`。纯中文名被清成空串
   → 400；中英混合名只剩下 ASCII 部分 → **200 报成功，但名字不是用户输入的那个**。
   后者比报错更糟：静默改写让用户以为自己改成功了。
2. **报错是纯英文**，面板原样显示，在中文界面上看不出所以然。
3. **面板改名框的 `onBlur` 是取消而不是提交** —— 输完名字顺手点一下别处（比如想看看效果），
   改动就被静默丢弃。这条与净化无关，单独就能造成"改了不生效"。

**tmux 到底支不支持中文名？** 实测支持：建会话、`send-keys -t 测试会话`、`capture-pane -t`、
`rename-session` 全部正常 ✓。真正必须排除的只有 `.` 和 `:` —— 它们是 tmux 目标语法
（`session:window.pane`）的分隔符，tmux 会把它们**自己归一成 `_`**（实测 `a.b` 与 `a:b`
撞成同一个 `a_b`），留着会让"UI 显示的名字"与"真实名字"对不上，之后按名字定位就找不到会话。

**修法**：

- 净化规则改为保留**任何语言的字母与数字**（`\p{L}\p{N}`）；`.`/`:` 显式折成 `-`（不给 tmux
  自己归一的机会）；其余（空格、`/`、`;`、`$`、emoji…）照旧折成 `-`；长度按**码点**截断
  （CJK 扩展区的字母是代理对，`slice` 会把一个字符劈成两半）。
- 净化是否改写了用户输入，由**宿主**判定并返回 `altered`（净化规则只有一处实现，面板不再重复实现）：
  面板显示中性提示（不是红色报错 —— 操作确实成功了），工具回一句
  `(name was sanitized: some characters are not allowed)`。
- 空名字的报错补上中文说明。
- 面板 `onBlur` 改为**提交**（与主流内联改名一致），Esc 仍是取消；输入框加 placeholder
  「名字（可用中文）」与提示文案；没改动就失焦时不再白跑一次请求。

**读代码时顺带发现两个连带缺陷**（都不是用户报的症状，但都由改名触发）：

- **`owners` 不跟着搬家**：它以会话名为键，改名后旧键的条目留在原地、新名字查不到 →
  `shell_list` 报 `owner=unknown`（实测确认）。后果不止显示：`enforceCaptureCap` 靠
  `owners[name].captureFile` 找留痕文件，丢了它就等于**这个 shell 的输出上限再也不会被执行**
  （留痕文件无限增长）。已在 `renameShell` 里搬家并落盘。
- **改名完全没有审计**：而改名恰恰改变了审计的主键 —— 不记的话，流水里会凭空出现两个名字，
  却没有任何一条记录说明它们是同一个 shell。已补 `event: 'rename'`，带 `renamed from <旧名>`，
  并区分来源（工具 / 面板）。

**怎么验证的**：新增 5.6 节 —— 纯中文名可用且在 `shell_list` 里原样出现；中英混合名保住中文；
不需要净化时不谎报"被改过"；需要净化时如实告知；`.`/`:` 被折掉；**归属跟着搬家**
（`test-session → test-session`，改动前会变成 unknown）；四次改名都进了审计流水（改动前 0 条）；
面板侧三条源码断言（失焦=提交、读 `altered` 标记、提示走中性 note）。原有净化断言
（`'other.x/y z' → dsh-other-x-y-z`、重复改名 → unchanged）保持不变 ✓。

**测试自己踩的一个坑**（记下以免重犯）：断言审计时用 `new Date().toISOString().slice(0,10)` 算日期，
而插件的 `dayKey()` 用的是**本地**时间 —— 在 UTC+8 的凌晨两者差一天，读的文件名根本不存在
（表现为"实到 -1 条"，一开始还以为是审计没写）。已改用与插件一致的本地日算法。

### 修复：输入 sudo 密码被守卫拦下（"提交前扫屏"一直缺一个前提）

**症状**（本轮用真实流程实测出来）：`sudo -i` 之后要把密码送进去，`shell_send` 返回

    REFUSED (privilege escalation).
    Detected in the line about to be submitted:
      [sudo] password for <用户>:

—— 守卫把**屏幕上的提示语**当成了"将要提交的命令"，密码必须靠 `confirm: true` 才送得进去。

**根因**：守卫有两道网。第一道扫本次调用带的 `text`（正确）；第二道是"提交时再看一眼当前输入行"，
用来拦分片拼装的命令，取法是**整屏最后一个非空行**。这个取法隐含一个前提：输入会被回显。
而密码提示恰恰**不回显** —— 于是"最后一个非空行"是程序的提示语而不是输入行，
`[sudo] password for <用户>:` 里含 `sudo`，被提权规则匹配上。

**为什么只有 sudo 中招**：ssh 的提示语是 `user@host's password:`，不含任何危险字样，
所以同一条路径在 ssh 下"看起来是好的"（实测确认：那一次是 `allowed`）—— 这正是它一直没被发现的原因。

**修法**：给第二道网补上它一直缺的前提 —— **只在前台确实是 shell 时才扫屏**。前台是密码提示、
TUI、REPL 时，屏幕上那一行根本不是"将要提交的命令"，扫它只有误报。前台探测失败时同样**跳过**
（照扫就会把本 bug 原样带回来）；取舍如实记下：漏掉的只有"分片拼装 + 恰好探测失败"这一种组合，
而第一道网（扫本次 `text`）始终在。顺带修两个小口子：`preKeys` 里带 Enter 也算一次提交
（此前只看 `keys`，而 preKeys 是先送出的，提交的恰是行上已有的内容）；拒绝文案改为
`Detected in the shell's pending input line`，如实说明是在哪一行发现的。

**这条修复依赖下一条**：`sudo -i` 里 tmux 报的前台是 `sudo` 而不是 root shell —— 前台判定本身就不准。

**怎么验证的**：新增用例造一个"假密码提示"（脚本打印 `[sudo] password for <用户>: ` 后 `exec sleep 30`，
前台因此**不是** shell，正是 sudo 开 `use_pty` 时的形态），先断言 `shell_list` 报 `fg=sleep`
（前提不成立的话，后面那条断言什么也证明不了），再断言此时送密码**不被拦**。反向同样钉住：
分片拼装（先送 `rm -rf `、再送 `/` + Enter）**仍然被拦**。

**顺手修掉一条空断言**：原来那条分片拼装断言写的是
`check(x.includes('REFUSED') || x.includes('idle') || typeof x === 'string', ...)` ——
最后一个分句恒为真，等于**没有断言**：这条回退哪怕整个失效也照样"通过"。已改为要求真的被拦下、
并要求文案指明来源。空断言比没有断言更危险，因为它给人"覆盖到了"的错觉。

### 修复：`sudo -i` 之后前台探测失效，idle 判定整段失灵

**症状**：提权到 root 之后，整个会话里每次 `shell_send` / `shell_read` 都报
`[foreground: sudo - not the shell; it may be waiting for input or still working]`，
直到 `exit` 才恢复 `[idle: shell prompt is back]`。

**根因**：前台名取自 tmux 的 `#{pane_current_command}`。Debian/Kali 默认开 `use_pty`，
`sudo` 自己在中间转发 I/O，**窗格的前台进程组始终是 sudo**，那个 root shell 是它的子进程。
于是"前台是不是 shell"这个判定在整个 root 会话里恒为假。

**修法**：从 `#{pane_pid}` 沿进程树往下钻，穿过后转进程（`sudo`/`sudoedit`/`su`/`doas`/`pkexec`/
`runuser`/`setpriv`）找到真正持有终端的那个进程（`drillForeground`，纯函数）。两条边界是刻意画的：

- **`ssh` / `wsl` / `docker exec` 不在表里** —— 它们的子进程在别的机器或别的命名空间里，本地进程树中
  根本没有那个 shell；报成 `ssh` 才是如实的（我们确实无法判定远端提示符），钻进去反而会给出**假的"就绪"**。
- **包装器有多个子进程时不猜**（`sudo bash -c 'a | b'`），保守退回原值 —— 等于改动前的行为。

**成本约束**：这条路径每次 send/read 都会走，所以进程树**只能读 `/proc`**
（`/proc/<pid>/task/<pid>/children` + `/proc/<pid>/comm`，整棵子树通常 2–5 个文件），
不能用 `ps` —— 经 subprocess 服务起一个进程实测 60–70ms，那等于给每个工具调用再加一拍。
已经是 shell 时**直接返回、一次 /proc 都不读**（绝大多数调用走这条短路）。非 Linux 或读失败时
退回原值，不会比改动前更糟。

**怎么验证的**：18 条纯函数断言穷举上述规则（含 `-bash` 登录形态、同名后代取最深、进程表有环时终止、
null/空表/pane_pid 缺失的退化路径）；真 tmux 端到端两条：空闲报 `bash`、跑 `sleep 25` 时报 `sleep`。
命令名与 `pane_pid` 在**同一次** `display-message` 里取，并用断言钉住"不额外 spawn"。

### 修复：光标被画到本行末尾

**症状**（用户报）：面板里插入点渲染在**本行最后**，不在真正的光标处。

**根因**：横向位置用 `Range` 实测"光标前那段文本"的渲染宽度 —— 方向是对的（中文由回退字体渲染时
advance 与等宽 ASCII 不同，任何"单元格 × 字符宽"的算法都会偏），但区间取的是**从屏幕第一行到
光标处**：那是个跨很多行的区间，而 `getBoundingClientRect()` 对多行区间返回的是**并集包围盒** ——
它的 `width` ≈ 最宽的那一行（通常就是整屏宽），于是 `left = padX + 整屏宽`，插入点被推到行尾。

**修法**：把区间限定在**光标所在的那一行**（行首 → 光标）。单行区间的包围盒就是该行前缀的真实宽度，
光标在行首时区间折叠、宽度天然是 0。**没有**改用 `getClientRects()` 取最后一片 —— 那在"光标正好在
行首"时有歧义（最后一片可能属于上一行，于是又画到上一行行尾）。行首的绝对下标就是
`offset - charIndex`，抽成纯函数 `prefixRangeOffsets(placement)` 便于离线断言。

**怎么验证的**：纯函数断言（区间 = 行首→光标、行首时折叠、无效输入返回 null、`charIndex > offset`
这种不自洽数据返回 null）；与 `caretPlacement` 串起来的端到端断言（三行屏幕、光标在第 2 行第 3 格
→ 区间必须是 4→6）；再装一个假 `createRange`，断言 DOM 路径**真的**用这两个端点调用
`setStart/setEnd`（从 0 起量正是本 bug 的根因），并覆盖两处夹取（`to` 越界夹到文本长度；
`from > to` 时两端收敛到同一点，否则 `setEnd < setStart` 会抛 IndexSizeError）。

### 提速：面板刷新（先量清每次请求的固定开销，再决定改哪里）

**症状**（用户报）：终端刷新慢、不跟手。

**先量再改** —— 这一步决定了改哪里：

| 端点 | tmux 调用次数 | 实测 |
|---|---|---|
| 静态资源 | 0 | 2ms |
| `/audit`（纯读文件） | 0 | 5–12ms |
| `/list` | 2 | 112–141ms |
| `/screen` | 2 | 124–166ms |
| `/diagnose` | 7–8 | 487–517ms |

裸调 `tmux capture-pane -S -200` 只要 **4.5ms**，而经 DSH 的 subprocess 服务起一个进程实测
**60–70ms**（每个命令各自一个 systemd scope：D-Bus 往返 + 建销 + 输出流收集）。所以延迟既不在
tmux、也不在载荷大小（`lines=0` 与 `lines=200` 耗时相同），而在**调用次数**。
按键回显 ≈ 70ms 去抖 + ~150ms 请求 ≈ **220–250ms**，与"不跟手"的体感对得上。

**改法一：把 `/screen` 的两次 tmux 调用合并成一次。** tmux 支持在一次调用里用 `;` 串多条命令、
输出按顺序拼接，于是 `display-message -p -F <LIST_FORMAT>` 走首行、`capture-pane -p` 走其余
（`captureWithMeta`）。切分无歧义：meta 是一行 tab 分隔的定长字段，会话名与命令名里都不含换行。
守卫那条"提交前扫屏"同样改用它 —— 否则为了给扫屏补上"前台是不是 shell"这个前提，
每次按 Enter 都要多一次 spawn（+65ms）。

**改法二：轮询改自适应。** 固定 700ms 意味着跑命令时输出最多滞后 0.7 秒；一味调快又会在空闲时白跑
（每次请求都是一次真实 tmux 调用）。现在：屏幕内容一变（或刚发过按键）切到快档 200ms，
静满 1.5 秒退回慢档 800ms。"在变"用文本比对判定，顺带让内容没变时 React 不必重渲染
（`setScreen` 传同值它自己会跳过）。发按键后的"立刻拉一次"会取消已排定的那次，
避免同一时刻并发两个请求。

**没有做的事，以及为什么**：没有绕过 subprocess 服务直调 `child_process` —— 那能把单次调用压到 ~5ms，
但会丢掉异常退出时的孤儿回收、超时的强制升级、输出上界与 spill 文件、环境清理、可执行文件校验、
进程树上的可归属性，以及"全部命令只有一条执行路径"的一致性。真正该走的是 **tmux control mode**：
一个长驻客户端（照样经 subprocess 服务起、照样在 scope 里、照样被 dispose 收掉），屏幕变化由 tmux
主动推 `%output`，而服务的输出收集是**基于偏移量、从不消费**的，因此增量读不产生 spawn ——
延迟能到 10–30ms 且上述保证一条不丢。那是独立的半天到一天工作量，本轮没做。

**怎么验证的**：真 tmux 断言 `captureWithMeta` 的六件事（一次调用拿到 meta、尺寸字段解析正确、
含光标与 paneHeight、屏幕行数 == paneHeight 说明 `trim:false` 保住了结尾空行、meta 首行没混进屏幕
文本、带 `-S` 历史时 meta 仍在首行）；另用一次性 socket 实测链式调用的输出形状（首行 15 个 tab
字段、总行数 = 1 + paneHeight）。

### 变更：看门狗的重启窗口 6 秒 → 60 秒

**为什么**：这两个常量决定的是"重启 `dsh web` 会不会把用户的 shell 全杀掉"。`systemctl restart`
期间存在一段**没有任何 dsh 进程**的真空期，脚本末尾那道 `pgrep -f "dsh web"` 守卫只能挡住
"新宿主已经起来"的情形，挡不住"恰好落在真空期里"的那一次 —— 一旦落在里面，`kill-server`
会连带清掉所有会话。6 秒（3 × 2s）太窄，一次稍慢的重启就会踩中。

**代价（如实记下）**：harness 被 `kill -9` 或崩溃之后，孤儿 tmux 服务端会**多活约 60 秒**才被收掉。
这是"重启不误杀"与"孤儿尽快收"之间的取舍，选前者 —— 误杀丢的是用户数据，晚收 60 秒只多占一点内存。

**发布前的一次修订（0.1.6 定稿）**：检测节奏从 `30 × 2s` 改为 **`6 × 10s`，总窗口仍 60 秒**
（用户两次点名：先 20s×3，再定稿 10s×6 —— 10 秒保留更细的判定粒度）。
看门狗是**长驻的 `sh` 循环**：每 2 秒探一次意味着每小时 1800 次 /proc+grep 唤醒，10 秒一次是
360 次（省 80%），判定语义不变（连续 6 次失败 ≈ 60 秒判消失，偶发读失败只 +1 不误杀），
"真正死掉后的反应时间"最坏同样约 60 秒。

**顺带修一条弱断言**：原来钉这个行为的是 `includes('-lt 3')` —— 而 `'-lt 3'` 是 `'-lt 30'` 的
**子串**，阈值改了也照样通过。现在把两个值提成具名常量（`WATCHDOG_MISS_LIMIT` /
`WATCHDOG_PROBE_SECONDS`），断言改为解析常量、要求乘积 ≥ 60 秒、并要求脚本确实引用了这两个常量
（防止常量与脚本脱节）。

### 修复：设置卡片与同页原生卡片错位（三处独立原因 + 一次"凭印象对齐"）

**症状**：设置 → 插件 → 插件配置里，本插件的卡片与同页原生卡片（bash / agent-loop /
subagent-model-selection / web-search）并排时明显不齐。用户的原话是"大小没设置好导致显示错位"。

**这不是一次事故，是两次。**

第一次（早先已修）：每一行各自是独立 grid，标签列宽弹性（`minmax(150px,220px)`）→ 每行按自己的内容
算一套列宽，输入框列在行与行之间对不齐。当时的修法是"所有行共用父级网格 + 行 `display:contents`"，
并且**用断言把这个结构钉住了**。

第二次（这次）：共用父级网格**仍然**错位。拆开是三个互相独立的原因，少修一个都不会好：

| # | 原因 | 后果 |
|---|---|---|
| ① | 网格 `minmax(140px,200px) / minmax(150px,220px) / minmax(0,1fr)` + 2×10px 间距 + 32px 内边距 ≈ **342px 最小宽度** | 面板窄时网格溢出卡片边框 |
| ② | 错误提示与只读提示是网格子项，却**没有** `grid-column:1/-1` | 提示挤进第 1 列，并把**其后每一行都推移一格** → 整张卡片错位（最显眼的一条） |
| ③ | 页脚是 body 的**兄弟**节点而非子节点 | 页脚不吃 body 的 `margin:0 16px` 内缩，宽度与上面的字段对不齐 |

测试也钉着 `radius: '12px'`、14px 标题、`1px solid border-l2`、输入框 `8px 12px`。
但官方 `@deepseek-ai/dsh-client-ui-settings-plugins` 的**编译产物里能直接读到真值** ——
它的 CSS Modules 以字符串内联在该包 `client.js` 顶部（`const css$3 = ".At1oFq_field{...}"`）。
逐项对照下来，**没有一项是对的**：

| 项 | 官方真值 | 旧代码（猜测值） |
|---|---|---|
| 卡片边框 | `.5px solid --dsw-alias-border-l4` | `1px solid --dsw-alias-border-l2` |
| 卡片圆角 | **16px** | 12px |
| 标题 | **15px / 600 / 1.4** | 14px / 600 |
| 副标题 | 13px / 1.5 | 12px |
| body | `border-top:.5px border-l2` + `margin:0 16px` + `padding-bottom:8px` | 无上边框，`padding:0 16px 12px` |

**修法**：整张卡片改成官方 `PluginCard` 的结构与几何 —— 根节点 `<li>`；字段纵向堆叠
（**根本没有列宽概念**，任何宽度都不会错位）；布尔项走官方 `SubagentModelSelectionCard` 的
`toggleRow`（标签左、开关右、两端对齐）；提示与页脚都是整行块；页脚回到 body 内部；
分组标题用整行 `<p>`，顺带**打断** `.field + .field` 的相邻关系（每组第一项不会带上分隔线）。
外观从内联 style 对象改为 `.dshsh-cfg-*` 类 —— 内联写不了 `:hover` / `:focus-visible` /
相邻选择器，而官方卡片的观感恰恰依赖它们。同时删掉一段**死 CSS**（`.dshsh-card*`，全仓无引用）。

**一个上游缺口**：官方 `.failed` / `.invalid` 用 `--dsw-alias-label-error`，但该令牌在实测皮肤
（blue-fantasy）的样式表里**没有定义** —— 也就是说官方那条错误色本身是失效的（会静默回落）。
本插件改用确实存在的 `--dsw-alias-state-error-primary`；`release:check` 的令牌白名单也拦下了前者，
顺带拦下了从官方抄来的硬编码 `#0000`（改成 `transparent`）。

**怎么验证的**：

1. `release:check` 当场抓到上述两个真问题 —— 说明那道闸是有效的，不是摆设；
2. 测试从"匹配源码字符串"升级为**渲染树结构断言**：用假 React 重建 `SettingsCard`，注入 4 个字段

### 新增：归属规则（可见性保留，但"不该随手动"写进提示与描述）

**用户问过的事**：能不能让 AI 只能看到/操作自己创建的 shell。**答案是"能，但选择不做强制隔离"** ——
跨对话保活与跨对话隔离本质互斥：shell 存在的意义就是"比创建它的对话活得久"，硬隔离会让用户换到新对话
后接不上自己刚建的 shell（以及让子代理看不到父对话的资源）。用户最终选择：**保留可见性，但明确要求
"没经用户明确要求，不要对不是你创建的 shell 做任何操作"**。

**落地**（三处一起，缺一处这条规则就会失效）：

| 位置 | 内容 |
|---|---|
| 系统提示（`USAGE_POLICY`） | 完整规则：`shell_list` 列出所有会话的 shell，每条带 `owner`；owner 是唯一能区分归属的字段；除非用户明确要求，不操作别人的 shell；面板不受此限制 |
| 4 个关键工具描述 | `shell_list` / `shell_send` / `shell_read` / `shell_close` 各带一句提醒 —— 模型"正要动手"时读的是描述，不是系统提示 |
| `release:check` | 机械守着：系统提示里必须有 `Ownership rule.`、必须有"除非用户明确要求"的例外、4 个工具描述里必须带提醒。反向验证：删掉规则 → 立刻 fail |

**一个副产品**：改 `shell_list` 描述时我顺手把原有的一句用途说明（"可用于判断是否还需要这个 shell"）
挤掉了，**测试立刻抓到**（`shell_list 描述里提示可用于判断是否还需要` ✗）—— 这正是既有断言的价值，
补回后两者并存。

### 修复：DSH 升到 0.1.5 后插件整体静默失效（工具/HTTP/面板全没了）

**现象**：用户升级 DSH 后，`shell_list` 变成 unknown tool、`/plugins/shell/list` 返回 404、面板消失。
日志里只有一句 `the subprocess service is not mounted`。

**根因**：`subprocess` 是**抽象服务**，具体 provider（`dsh-subprocess-local`）由 `dsh-base` 挂载。
DSH 0.1.5 起组合顺序变了，provider **晚于**本插件挂载 —— 而插件在 apply 期用一次性
`ctx.get('subprocess')` 取它，拿到 `undefined` 就早退，于是工具注册、HTTP 路由、客户端面板**全部没有发生**。

**这与之前 `settings` 踩过的是同一类坑**（那次已经写成"必须用 `ctx.inject` 延迟注入"的注释），
只是这次踩在了另一个服务上。修法是把 `subprocess` 声明进模块级 `inject`：
`export const inject = ['tools', 'subprocess']` —— Cordis 会等它就绪再调 apply。

**顺带查出同一类的第二处**：审批情报在 apply 期一次性读 `ctx.get('approval')`，注释写着"动态读"
但实现是一次性的（注释与代码不一致）；更糟的是它引用的 `approvalService` **从未定义**，
而那句 `approvalService?.overrideOf(...)` 被 `try/catch` 吞掉 ——
于是"会话级审批策略覆盖"这条路径**从来没生效过**，永远回落到部署默认值。
两个 bug 一起修：把全部读取挪进 `approvalInfoFor()`，在调用时读。

**回归防线**：`release:check` 新增不变量 —— `inject` 必须包含 `subprocess`，且不允许再出现
apply 期的一次性 `approval` 探测。反向验证：把 `subprocess` 从 inject 去掉 → 两条信号同时触发。

**教训（已写进文档）**：凡是"抽象服务 + 具体 provider 另行挂载"的东西，都不能在 apply 期一次性
`ctx.get` —— 要么声明进 `inject`，要么用 `ctx.inject([...])` 延迟注入。宿主升级会改组合顺序，
而这类失效是**静默**的（插件不报错，只是什么都没注册）。

### 新增：权限模型（时间 × 能力）与"不被反复询问"

**需求演进**：先是"能在面板主动授权"（避免每个新对话被问一遍）→ 然后"授权要更细"。最终定稿为两个维度：

| 维度 | 档位 | 说明 |
|---|---|---|
| 能力 | 完全控制 / 只读 / 完全禁止 | 只读 = 能看不能输入；完全禁止 = 碰不到插件功能，但**查授权状态不受影响**（用户明确要求） |
| 时间 | 10 分钟 / 30 分钟 / 2 小时 / 永久 / 自定义 | 自定义范围 1 分钟 – 30 天（用户拍板） |

**实现上的三个关键决定**：

1. **能力映射表放在 `lib/consent.js`，并且工具注册统一包一层 `guardedTool`**。理由：11 个工具 × 3 个档位，
   分散写必然漏一个，而漏一个就是安全缺口。集中之后新增工具自动被管住；未登记的工具按
   "需要完全控制"处理（fail closed）。`scripts/test-consent.mjs` 会**交叉校验**
   `index.js` 实际注册的工具与映射表**完全一致** —— 加了工具忘了登记会立刻红。
2. **`shell_consent` 的能力要求是 `none`**：任何档位都不拦它。这是用户明确要求（"完全禁止也要能查"），
   否则模型没法解释自己为什么被挡。
3. **`shell_close` 需要完全控制**：关闭会杀掉里面的进程，不算"只看看"（用户拍板）。

**"不被反复询问"的三层机制**（这是用户最后一条要求）：

1. **冷却期**（`consentRetryCooldownSeconds`，默认 600 秒）：被拒绝或超时后，同一对话在这段时间内
   **不再询问、直接拒绝**，并明确告诉模型"不要再问、也不要换个说法再问"。没有这一层，模型会在每次
   工具调用前重复弹同一个问题 —— 这是"重复询问"的真正根因。
2. **并发只问一次**：同一对话的并行调用复用同一个提问（已有）。
3. **「完全禁止」是持久的"别再问"**：设成该档后永久不再询问。

**UI**：盾牌按钮打开授权浮层 —— 上半部「默认授权（所有对话）」选能力档 + 时间档（含自定义分钟数）并应用；
下半部「已授权会话」按**最近使用排序**、显示**会话标题**（来自 DSH 的 `session/title` 事件，
`ctx.sessionQuery.readTitle()` 读取；SessionHeader 本身没有名字字段）、档位、剩余时间，可**逐条撤销**；
最近的那条标注「最近使用（很可能就是当前对话）」—— 这正是用户提出的"会话多了列表很长、找不到当前会话"
的解法。档位目录由宿主 `GET /consent` 下发（`catalogs`），面板不硬编码，避免两边漂移。

**踩到的两个实现坑（都记下来）**：
* **判定顺序**：「完全禁止」必须**先于**"已有授权 → ok"判定。否则选了禁止之后返回的是 `ok: true`
  （只是 scope=deny），最后只得到一句通用的"能力不足"提示，用户"禁止"的语义被弱化 ✗。
* **旧格式兼容**：本模型之前的 `consent.json` 里没有 `scope` 字段，那时授权就等于完全控制 ——
  按 `full` 兼容读取，否则升级后所有旧授权突然失效、人被重新问一遍。而"有 scope 但值非法"仍拒绝。

### 新增：面板头部的授权按钮（主动授权 / 立即撤销，且落盘保留）

**动机**：首次使用确认门是按对话问的 —— 换个对话就要再问一次。用户在面板顶部要一个按钮，
能主动授权（避免被反复询问），也能立刻收回授权；已经存在落盘持久化（`consent.json`）必须保留。

**设计上的一个硬约束**：面板跑在**浏览器侧**，它不知道"当前是哪个对话"（actor 只能记到 `panel`）。
所以面板能表达的主动授权只能是**通配语义**（所有对话都放行）——不能用逐对话授权来假装精确。
实现上用 `consent.json` 里一个保留键 `'*'`：

* 文件格式不变（仍是「键 → 授权信息」的字典），**旧文件天然兼容**，不需要迁移；
* 判定顺序：通配 → 逐对话 → 问人。通配优先，因为它是用户主动按下的，而不是被追问出来的；
* **撤销**一次清掉通配与全部逐对话授权 —— 这也让面板成为唯一能"一键收回所有授权"的地方；
* 写入**必须 await 落盘**：失败就回 500 并如实报错，避免"界面显示已授权、重启后复活"。

**语义与安全的取舍（写进了文档）**：撤销管的是"能不能再动它"，**不会关掉已经开着的 shell**；
方向安全的一侧（撤销）点一下即生效，危险的一侧（授权所有对话）用两步确认（3 秒内再点一次），
与关闭按钮同一套语义。`requireConsent: false`（已放弃闸门）时按钮禁用并说明原因，不假装还有用。

**验证**（`scripts/test-edge.mjs` 7.97）：GET 初始状态 ✓、非法 action → 400 ✓、授权后 `allowAll=true` ✓、
**授权后新对话第一次用工具不再被问** ✓、`/list` 带出状态（面板不必另开轮询）✓、撤销后
**新对话重新开始询问** ✓、两次写入都**立刻落盘**（直接读 `consent.json` 断言）✓。
客户端侧另有 21 项断言覆盖按钮模型（未授权/已授权/配置关闭三种形态与文案）。

### 安全：开发机信息从整部 git 历史里清掉

**问题**：0.1.0–0.1.4 的已发布包里，`PUBLISHING.md` 含开发机绝对路径
（`/home/<用户名>/DeepSeek_Harness/dsh-agent-shell`），`scripts/test-client.mjs` 含同一用户名，
`scripts/test-edge.mjs` 含内网地址 `192.168.1.9`。工作树后来修好了，但**历史提交里还在**，而仓库是
公开的：`raw.githubusercontent.com/<repo>/v0.1.4/PUBLISHING.md` 实测 HTTP 200，任何人都能读到。

**根因**：漏扫范围错位 —— 泄露检查只覆盖 `lib/*` 与 `package.json`，文档与脚本从来没进过扫描范围；
修掉工作树也不等于修掉历史。

**处理**：从**全部提交与标签**里替换这三个标识（`git filter-branch --tree-filter` +
`--tag-name-filter cat`），清掉 `refs/original` 备份引用、`git gc --prune=now`，然后强推 main 与
6 个标签。替换后逐项验证：

| 验证 | 结果 |
|---|---|
| 202 个历史 blob 全量重扫（路径/主机名/邮箱/IP/密钥/用户名 12 类模式） | 只剩 `/home/u`、`192.0.2.9` 这类中性占位符 |
| `git grep '<开发机路径>'` 在 HEAD 与 v0.1.0–v0.1.5 全部标签 | 0 命中 |
| 远端引用 SHA 与本地逐一比对 | 完全一致 |
| GitHub 上旧标签的 `PUBLISHING.md` 第 107 行 | 由开发机绝对路径变为 `cd ~/dsh-agent-shell` |
| 作者邮箱（全历史 32 个提交） | 只有 GitHub noreply，无个人邮箱 |

**已知残留（必须如实说明）**：GitHub 对「不再被任何引用指向」的旧对象**仍会按 commit SHA 直接
返回**（实测旧 v0.1.4 提交的 `PUBLISHING.md` 仍能取到那句路径，GitHub API 也返回 200）。改写历史只能
让旧内容不再沿任何正常路径暴露，彻底清除需要向 GitHub Support 申请清除无引用对象与缓存视图 ——
申请模板与步骤见 [PUBLISHING.md](PUBLISHING.md) 第 8 节。

**为什么加了两道扫描而不是只加一道**：`release:check` 只扫工作树，它拦不住「工作树修好了、历史提交
里还留着」—— 那正是这次发生的事。所以新增 `npm run leak:history`（扫全部历史 blob + 全部标签，
报出 sha / 路径 / 行号 / 文本，并列出命中出现在哪些提交上）。两者共用
`scripts/lib/leak-rules.mjs`：规则分散在两处就一定会有一处跟不上，这次已经把规则从
`release:check` 里抽了出来。

**规则本身也有洞（拿旧镜像跑一遍才看出来）**：最早的路径规则要求结尾带斜杠
（`/home/<user>/`），而历史里的另一处泄露是**测试夹具里一行裸路径**（后面紧跟引号）——
整类写法被漏掉。规则收紧为「不要求结尾斜杠」，由占位符白名单（`/home/u`、`/home/user` 等）负责
放行假路径。反向验证：用改写前的备份镜像跑 `leak:history`，命中数从 3 处升到 **17 处**
（`PUBLISHING.md` + `scripts/test-client.mjs` 全部被抓出来），而当前仓库仍然 0 命中。

### 流程：公开仓库只留版本级提交，粒度历史只进私有备份

维护者要求的目标是：**公开仓库只能看到版本级更新，中间细节不可见也不应该可见**；只有决定发下一个版本时
才动公开仓库；而开发过程中又要能随时回滚，所以粒度更新持续推给**私有**仓库。

这三条会互相冲突，得说清机制才能同时满足：

* **推一个分支 = 推它的全部祖先提交**。所以「平时不推、发版才推 main」**并不能**让中间提交消失 ——
  发版那一刻它们会一次性出现在公开历史里。要让公开历史只有版本级提交，必须**压缩**：
  把自上个 tag 以来的全部提交 `git merge --squash` 成一个 `release: <版本>` 提交。
* **压缩不改内容**：脚本会校验「发布提交的树 == 开发树」，不一致就中止且不推送 —— 发布出去的必须是
  测试过的那份代码。
* **粒度历史不能放公开仓库**：在公开仓库开 `wip`/`dev` 分支是无效的（分支一样公开可见）。
  所以粒度提交只推私有远端；发版时先把当前粒度顶端归档成 tag，避免被下一轮覆盖后彻底丢失。
* **可见与不可见**：单个 `release:` 提交的 diff 仍然体现「这个版本改了什么」—— 那是发版本身要传达的信息；
  被隐藏的是**过程**（粒度、提交信息、中间状态）。

落地为两个脚本 + 两处文档：

| 位置 | 内容 |
|---|---|
| `scripts/backup-push.sh` | 粒度历史备份到**私有**远端；会先问 GitHub API 确认目标不是公开仓库（公开就拒绝） |

## 0.1.5 — 首次使用需用户确认（授权门）+ 依赖自检脚本 + 文档调整

### 新增：授权门（`requireConsent`，默认开）

规则：一个对话**第一次**要用本插件的工具（`shell_open` / `shell_send`）时，先向用户确认一次；
同意就等于授权该对话在这些 shell 上执行**任意命令**，之后同对话不再询问。

九个必须处理好的细节（都有断言）：

- **只授权当前对话**，换对话各自确认；授权落盘（`consent.json`），热重载/重启不重复问。
- **拒绝必须真的挡住**：不创建 shell、不发送任何输入 —— 断言的是"没有副作用"，不是"回了一句话"。
- **面板（人）不过门**：那是你自己在操作，不该问"允不允许你自己"；但会记一条审计。
- **子代理没有人可以问**：DSH 的提问服务不向子代理转发问题（问了会**永久阻塞**）。本进程内已有人类
  授权则**继承**并如实记为 `inherited`；否则拒绝并说清"先让用户在主对话确认一次"。
- **没有提问服务时 fail closed**：问不到人就不算得到授权，拒绝并指出配置出口 `requireConsent: false`。
- **并发只问一次**；**拿不到会话身份时拒绝**（不能把授权记到别人头上）。
- **每次确认/拒绝/继承都进审计**；问题措辞里明确写「授权执行任意命令」，不含糊成"是否继续"。

### 新增：`install-deps.sh`（依赖自检与安装）

```sh
./install-deps.sh --check   # 只读体检：缺什么 + 确切安装命令（不 sudo、不改系统）
./install-deps.sh --yes     # 装上缺的（会 sudo，只装缺的）
```

看不懂的 spawn 错误。**用户只要说「帮我装 dsh-agent-shell」，AI 读 README 就能跑这个脚本。**

### 修复：设置页卡片（"注册成功却看不到"的真根因）

DSH 设置页渲染的是两份账本的交集：宿主提供的 settings namespace，**与**注册进

且该插槽是 keyed 的、**key 必须等于 namespace**，不一致时**静默不渲染**。此前只做了宿主侧注册，
所以卡片永远不出现。现在客户端补上卡片（key = `dsh-agent-shell`），并通过插件自己的 `/settings`

越界当场拒绝并给范围、保存后显示宿主结论（立即生效 / 需重启）；无设置服务时只读并说明原因。

### 修复：光标的三次偏差

1. **文本少时不显示**：`screen()` 裁掉结尾空行 + 行号按「行数 − paneHeight + cursorY」换算 → 负数。
   现在面板路径保留完整窗格（实测 trim=true/−21 vs trim=false/1），工具路径仍裁空行。
2. **输入中文后偏后**：用「单元格列 × ASCII 字符宽度」算像素 —— 只在 CJK 宽度恰为 ASCII 两倍时成立，
   而中文常由回退字体渲染（advance ≈1em vs ASCII ≈0.6em）→ 文本比网格窄、光标偏右。
   现在改为把插入点作为**零宽内联元素**插入文本流，位置完全交给浏览器排版（零像素计算）。
3. **文本少时画偏**：行高曾从 `scrollHeight` 推，而它取「内容高度 / 可视高度」较大者 → 内容矮时被高估。
   行高改读计算样式（`normal` → 字号 ×1.2），量不到不画；滚动补偿同样改用实测行高。

### 新增：真实光标（只在解锁后显示）

面板是文本快照、不画插入点 → 打空格/Tab 时不知道下一个字符落在哪一列。现在：

- 从 tmux 取 `#{cursor_x}/#{cursor_y}/#{cursor_flag}/#{pane_height}`（并入**已有的** `list-panes`，
  零额外进程），客户端画一个闪烁插入点；
- **只在解锁后显示**（用户明确要求）：锁定时不画 —— 那时那个位置不代表用户下一个字符的落点；
  程序隐藏光标（TUI）时也不画；
- 难点如实处理：`cursor_x` 是**单元格列**而不是字符下标（汉字/全角标点/emoji 占 2 格、
  组合符占 0 格、半角片假名占 1 格），所以实现了 cell→char 映射；`cursor_y` 相对可见窗格，
  按"可见窗格贴底"换算成文本行号；
- **算不出来就不画**：无 meta / paneHeight 缺失 / 量不到字符宽度 / 光标在取景窗口之外 → 一律不画；
- 绝对定位在 `<pre>` 内容坐标里，随内容一起滚动，无需额外同步滚动位置。
- **修复"文本少时光标不显示"**：`screen()` 默认裁掉结尾空行，而光标行号按
  「文本行数 − paneHeight + cursorY」换算 —— 文本少时（窗格下方为空）行数不足，算出负数 → 不画。
  现在 `/screen`（面板）保留完整窗格，工具路径（`shell_read`）仍裁掉空行。实测：trim=true 时
  2 行 → 行号 −21（画不出来），trim=false 时 24 行 → 行号 1。
- **修复首版的行高 bug（"文本少时光标偏、文本多正常"）**：`scrollHeight` 取「内容高度」与
  「可视高度」中的较大者 —— 内容比视口矮时它等于视口高度，`(scrollHeight − padding) / 行数`
  会把行高算成几十像素（真实约 17.5），光标因此被画到下面；文本多了内容高于视口才正常。
  现在行高来自计算样式（`normal` 时按字号 ×1.2 估），量不到就不画；**滚动补偿**同样的高估
  也一并改用实测行高。两者在"文本少"时的差异已写成回归断言（连旧算法的错误结果一起钉住）。

### 安全（0.1.5 之前那批，原「未发布」节）


从「权限太大」这个疑问出发，把攻击面按**可达路径**逐条过了一遍（不再是笼统的清单），修掉两个真问题：

- **跨站请求伪造（可被任意网页打成远程命令执行）**：面板的 HTTP 路由在 `127.0.0.1` 上、
  无鉴权，而我访问的任意网页都可以 `fetch('http://127.0.0.1:3080/plugins/shell/keys', …)`。
  修复前的关键缺口是**请求体解析完全不看 `Content-Type`**：跨站「简单请求」（`text/plain`、表单）
  不触发预检，响应虽然读不到，但**命令已经执行**。现在：拒绝 `Sec-Fetch-Site: cross-site`、
  `Origin` 必须与 `Host` 同源（含拒绝 `Origin: null`）、**写请求必须是 `application/json`**
  （强制预检，而本插件不返回任何 CORS 头 → 浏览器发不出去）。
- **DNS rebinding（可读走终端内容并写入）**：攻击者域名解析到 `127.0.0.1`，浏览器视为同源即可读写。
  现在 `Host` 必须是回环地址且端口等于实际监听端口。
- **配置值 → 命令注入**：`socket` 名会被派生成 `/tmp/<name>-tmux.conf` 与 `-watchdog.pid`，
  而这两个路径此前**无引号**拼进 `sh -c`（6 处）—— 名为 `dsh; rm -rf ~ #` 的 socket 就是注入。
  现在 `socket` 在解析处收敛到 `[A-Za-z0-9._-]`，且所有 shell 插值统一单引号转义；被改写时
  面板与诊断**如实说明原值**（静默改名会让人找不到自己的会话）。
- 闸门在**路由注册处统一包裹**：以后新增路由不可能忘记防护（纵深防御靠结构，不靠自觉）；
  若部署挂了 DSH 的 `connection` 服务则优先采用它的 Host/Origin 围栏与浏览器会话校验
  （那条能连「本机其它进程」一起收口），没有则用本地等价实现。
- 如实公开**降级路径**：服务绑到 `0.0.0.0` 时 `Host` 无法判定是否本机，闸门降级并在面板上以 `⚠`
  标出；「本机其它进程能驱动这些 shell」属于**接受的风险**（端点本身等价于本机 shell 权限），
  已写进 `SECURITY.md` 第 1 与第 8 条，不再含糊。
- 新增 `allowedHosts` 配置（默认空）：闸门默认只信回环 `Host`，而**反向代理部署**（`SECURITY.md`
  自己推荐的加固方式）转发过来的 `Host` 正是别的域名 —— 不处理就会把面板自己关在门外。
  白名单只放宽 `Host` 判定，跨站/JSON 两条检查照旧；不接受 `*`（那等于悄悄关掉防护），
  条目形状由设置页校验，改完**立即生效**。
- 面板 ⓘ 新增「**浏览器面闸门**」一行（谁在把关、绑定地址、被拒次数、降级警告），
  被拒的请求会留记录 —— 否则「面板突然打不开」无从查起。

测试新增 39 项断言（宿主侧），其中最关键的是**反向对照**：同一个 `POST /keys`，带攻击头 → `403`
且**命令没有执行**；去掉攻击头 → `200` 且命令真的执行 —— 这才证明「是闸门挡下的」，而不是
「命令本身没跑起来」。另外用恶意 socket 名**真跑一次** `sh -c`，断言注入标记文件没有生成。

## 0.1.4 — 可审计（输入流水 + 输出留痕 + 归属）与「开箱即用」

### 新增：审计

跨对话保活是这套机制的核心价值，代价是**任何对话都能看到并操作任何 shell**（实测：在 A 对话里
`shell_list` 就能列出 B 对话创建的 shell）。既然隔离与保活互斥，那就把「事后查得清」做扎实：

- **输入流水**：进入终端的字节只经过两个入口 —— 工具的 `shell_send` 与面板的 `/keys`，
  所以在这两处记账即**完整**。每条记录含时间、shell 名、来源（tool/panel）、
  **发起会话 id**（`exec.agent.session.id`；面板侧只能记 `panel`）、text/keys、护栏决策与结果。
  **被护栏拦下的企图同样留痕** —— 只记成功的审计等于把最该看的藏起来。
- **输出留痕**：每个会话用 tmux `pipe-pane` 把终端输出（含回显的命令、程序输出、TUI 画面）
  原样追加到 `output/<shell>-<起始时间>.log`，**会话关掉后文件仍在**（实测保留字节并命中标记）——
  这就是"关闭会话后依然可见"。默认单会话上限 64 MiB，触顶自动停止留痕**并记一条审计**
  （磁盘上少了一段，必须有人知道）。
- **归属标注（D1）**：`shell_open` 记下发起会话 id，`shell_list` 显示 `owner=…` 或
  `owner=panel`；插件之外建的会话如实标 `owner=unknown`。**只标注、不拦截** ——
  非 owner 依然可以操作，这条被测试刻意钉住，避免以后被误改成隔离。
- **查询面**：新增 `shell_audit` 工具与 `GET /plugins/shell/audit`（面板 ⓘ 用），
  支持按 shell / actor / source / 天数过滤；面板 ⓘ 新增「审计」「输出留痕」两行，
  如实显示目录、保留期、上限、以及**写失败**（审计不可信时不能装作有）。
- 落盘：`${DSH_HOME:-~/.dsh}/agent-shell/`，目录 0700、文件 0600，按天轮转、默认保留 30 天
  （过期文件在启动时清理）。可用 `auditDir` 指到别处（例如加密卷）。

### 修复：开箱即用

在另一台机器上装 0.1.2 暴露出两个真问题：

- **pnpm 报缺 peer**（`Issues with peer dependencies found`）：profile 的 pnpm 配置是
  `autoInstallPeers: false`，peer 本应由 DSH 的**模块代理**在启动时提供，而我们把四个
  peer 声明成了必装 —— 包管理器于是要么报警告，要么（npm）真装进来一份 **第二实例**的
  cordis/dsh-tools（比警告严重得多）。现在四个 peer 全部标记 `peerDependenciesMeta.optional`
  （名字仍在 `peerDependencies` 里，DSH 的代理机制照旧生效），实测 `pnpm peers check` 输出
  `No peer dependency issues found`。
- **tmux 是系统依赖，包管理器不会提醒**：没有 tmux 的机器会"装成功"，然后在第一次开会话时抛

  控制台与 `shell_diagnose` 给出**可执行的安装指引**，`shell_open` 直接返回同一条提示，
  面板 ⓘ 新增「tmux」一行并以 ⚠ 标出。缺什么就说清什么，这才叫开箱即用。

## 0.1.2 — 设置页真正可用（并修掉一个静默失效）

### 修复

- **设置功能此前一直是坏的：卡片看着注册上了，改设置却永远不生效。**
  根因：`state` 被声明在设置注册**之后**，而官方 `installSection` 在注册时会**同步**回调一次
  `onChange` → `applyResolved` → 读 `state` → TDZ `ReferenceError`，异常被注册用的 `try/catch`
  吞掉。后果不是「报错」而是**静默失效**：`scope.watch` 根本没挂上，之后的写入不再触发回调。
  改法：把 `state` 提到注册之前，并在代码里写清这个顺序为什么不能动。
  这个 bug 能藏住的原因值得记一笔 —— 旧断言只检查「注册桩被调用过」，而这些在崩溃**之前**
  就已经成立。现在断言的是**结果**：注册日志里不该有异常、面板 note 必须是成功文案、
  `validate` 必须收到套过默认值的完整配置、组合配置越界时必须不崩且如实告知。
- **`/list` 的 `settings.live` 不再谎报**：它原先只表示「设置服务挂载了」。现在
  `live` = 用户**真的能在设置页改**（注册成功），并分开报告 `service` / `registered`；
  组合配置越界时面板写「设置页未注册：<原因>（插件仍按组合配置运行）」，
  而不是谎称可用、让用户去设置页找一张不存在的卡片。
- **看历史时不再被新输出顶上去**：屏幕取景窗口是「最后 N 行」，新输出会把**最上面**的行挤掉，
  所以「`scrollTop` 没变」并不等于「阅读位置没变」。旧实现只在贴底时才滚 —— 翻上去之后确实
  不滚了，但内容整体上移仍会把你正在读的那几行顶走。现在：**贴底照旧跟随；非贴底按内容
  整体位移补偿**（窗口下滑 K 行补 K 行高度；点「更多历史」在顶部插入 P 行则反向补偿 P 行）。
  判定抽成纯函数 `scrollAnchor()` / `contentShift()`，判不准（内容被整屏换掉、整屏都是重复行、
  重叠不足 3 行）时**宁可不补偿也不乱跳**。行高按 `(scrollHeight − padding) / 行数` 精确计算，
  内边距由 `SCREEN_PAD_Y` 同时供给样式与补偿，避免两边各自写死而漂移。
- **切换 shell 时回到「跟随最新」**：在 A 会话翻着历史（已脱离底部）再切到 B 会话时，
  阅读位置被带了过去 —— 新会话停在半空、不跟随。现在 `expanded` / `currentName` 变化即重置为
  跟随；「更多历史」翻倍窗口**不会**重置（那是同一个视图，位置要保持）。

### 新增

- **设置页真正可用**：`ctx.settings.installSection` 注册 `dsh-agent-shell` namespace，
  在 **DSH 设置 → 插件**里直接改 **14 个参数**，不必改 `cordis.patch.yml`、多数项也不必重启。
  **每个字段都带 `.description()`** —— 设置页的表单就是由 schema 生成的，没有说明的字段在
  用户眼里只是一个光秃秃的键名（`httpBase` 是干什么的？），所以说明里逐条写明**立即生效**还是
  **需重启**。两条机械不变式守着它：新增字段漏了说明 fail；说明没写清生效时机也 fail。
- **设置页取值校验**（`validateSettings`）：`cols` 20–1000、`rows` 5–500、`historyLimit`
  100–1000000、`maxSessions` 1–64、`socket` 只允许字母数字下划线短横线、`httpBase` 必须以 `/`
  开头、`shell` 不能为空 —— 越界**当场拒绝并给出范围**（`cols 必须在 20–1000 之间（现在是 5000）`），
  不再悄悄改小。schema 本身保持宽松：`cordis.patch.yml` 里的越界值仍按老规矩在用时夹住，
  不会因为一条 YAML 就让插件装不上。
- **面板 ⓘ 详情层新增「参数设置」一行**，三态如实分开：

  | 显示 | 含义 |
  |---|---|
  | `已接入（DSH 设置 → 插件里改）` | 注册成功，现在就能去设置页改 |
  | `未注册：<原因>` | 服务在、但注册被拒（例如 `shell 不能为空`）；悬停看完整原因 |
  | `未知（宿主未上报，需重启 dsh web）` | 老宿主（0.1.2 之前）的 `/list` 里没有这个字段 —— 如实说不知道，不猜成「已接入」 |

- 新增的关键不变式：每个参数必须有说明、说明必须写清生效时机、注册必须真的成功（而非

## 0.1.1 — 生命周期修复：不再误清会话

0.1.0 发布后在真机上观察到一次「看门狗静默死亡 + 会话被清」的事故，根因是两个用**进程命令行
字符串匹配**认人的判断。本次修掉它们，并补上自愈与回归测试。

**修复**

- **不再靠字符串匹配认 harness**：`harnessPid()` 原先向上找「cmdline 里含 `dsh` 的祖先进程」，
  实测会被**任何**命令行里提到 dsh 的中间进程骗到（真实踩到：一条内容含 "dsh" 字样的
  `bash -c "…"` 被当成了 harness）。改用本进程 pid（插件与 harness 同进程），只在非常规部署下
  才退回向上遍历，且取**最上层**匹配项。
- **启动时不再清理会话**：pid 文件对不上时旧实现会清掉服务端上的全部会话，而它区分不出
  「上次崩溃的残留」与「热重载/重启后幸存的会话」。现在只在「收养已有看门狗」与「重新布防」
  之间选择，**一只会话都不动**。
- **看门狗守卫真的生效了**：原来的 `pgrep -f "dsh web"` 会匹配到看门狗**自己**（脚本文本里就含
  这个字面量），导致守卫恒为真、`kill-server` 永不执行 —— 孤儿兜底等于完全失效。现在排除自身
  pid，并已用「有/无其它实例」两种情形分别验证。
- **存活判定容忍连续失败**：旧写法一次读取失败就让看门狗**永久退出**，从此再无兜底且无人知晓；
  现在连续 3 次（约 6 秒）失败才判定 harness 消失 —— 顺便给快速重启留出窗口。
- **看门狗自愈**：每次操作（5 秒节流）确认看门狗仍在，不在就重新布防并写日志。

**行为变化**

- **重启 `dsh web` 现在通常能保住 shell**：快速重启时看门狗会发现新宿主而不收服务端，新宿主
  复用已有服务端。宿主停机超过约 6 秒（崩溃、慢重启）则仍会被看门狗收掉。
- 启动时不再有任何「清孤儿」动作；想清空请显式 `killServer()` / `shell_close`。

**面板融入 DSH 原生主题**（之前是**一块突兀的黑板子**）

面板原先引用的 `--dsw-alias-bg-primary` / `--dsw-alias-border-primary` 这两个令牌**在 DSH 里
根本不存在**，于是永远落到硬编码的深色上 —— 深色主题色偏，**浅色主题下就是黑板**。按 DSH 的
真实设计语言重做（令牌名与取值取自 `dsh-client-ui-theme`）：

- 表面层级：面板 `bg-layer-1`、弹层（选择器 / ⓘ）`bg-layer-3`、终端区
  `markdown-code-segment-unselected`、输入框 `bg-layer-2`；
- 文字三级：`label-primary` / `label-secondary` / `label-tertiary`；
- 描边统一 **0.5px 发丝线**（DSH 全库只用 .5px）`border-l1` / `border-l2`；
- 按钮改用专用令牌：标题栏 `button-tool-bar-fill/hover`、悬浮胶囊 `button-floating-fill`、
  开关态 `button-ghost-active-fill/border`、主操作（＋）`button-primary-fill` +
  `label-primary-inverted`、危险 hover `interactive-bg-hover-danger`；
- 行 hover / 选中：`interactive-bg-hover` / `interactive-bg-active`；
- **去掉全部装饰性彩色**（原来的蓝色强调）—— DSH 的原生强调是单色的（`brand-primary` 在亮色下
  近黑、暗色下近白），彩色只保留给状态：`state-success/warn/error-primary`；
- 投影由 `0 16px 48px rgba(0,0,0,.5)` 改为轻量的 `0 6px 20px bg-mask-1`。

现在**零硬编码颜色**，亮色/深色两套主题都自动跟随。`npm run release:check` 新增两条不变量
防止复发：客户端引用的每个 `--dsw-*` 令牌必须在官方令牌表内（写错名字会静默回落到 fallback
颜色，浅色主题下必然出错），且不允许出现硬编码颜色字面量。

**安全与知情**（如实告知，而不是加一层防护）

本插件没有接入 DSH 官方审批（`dsh-user-approval` / `tools/pre-execute` → `ctx.approval.request`）。
原因是平台设计上的互斥：官方权限预设把 `danger-full-access` 的策略定为 `never`，而本插件**必须**
`danger-full-access` 才能工作（受限模式下 tmux 服务端无法跨调用共享）。所以不去假装接入，
而是**把这件事如实暴露**：

- `/list` 与 `/diagnose` 新增 `approval` 字段：审批缝是否挂载、权限模式、以及按官方公式推出的
  策略（`never`/`ask`）与一句风险说明。
- 面板状态行新增 **`审批 never`** 标记（`never` 时标红），悬停给出完整风险说明；版本号悬停里
  注明「本插件由 AI 开发，未经人工安全审计」。
- README 顶部醒目告警章节：这是真实 shell、AI 可执行任意命令、没有任何审批弹窗、唯一防线是
  可被绕过的启发式护栏，并给出「什么场景不要用」的对照表；`SECURITY.md` 同步加入
  「没有接入官方审批，而且在这个模式下也接不进来」一条。
- 明确声明：**本插件由 AI 开发，未经人工安全审计。**

**边界与错误路径**（由新增的边界测试套件发现，六个真 bug）

- **会话名里带 `.` 会导致会话彻底失联**：`shell_open` 的净化规则与 `shell_rename` 不一致
  （前者保留点号），而 **tmux 会把名字里的 `.` / `:` 悄悄换成 `_`** —— 于是插件以为叫
  `dsh-a.b`、tmux 里却叫 `dsh-a_b`，之后所有按名字的操作都以 `can't find pane` 失败。
  现在两条路径共用同一套净化规则。
- **服务端刚退出时建会话有约 50% 概率失败**：关掉最后一个 shell（或显式 kill-server）之后立刻
  `new-session`，tmux 会报 `server exited unexpectedly`（实测 8 次失败 4 次，加 300ms 延迟则
  0 次失败）。`create()` 现在按 300/600ms 退避重试，最多 3 次。
- **`cols`/`rows` 没有上限**：荒谬尺寸（如 `cols: 100000`）会把 tmux 的 `width too large`
  原样抛给调用方。现在统一夹到 `1000×500`（下界仍是 20×5）。
- **不存在的 `cwd` 会让工具谎报工作目录**：tmux 对 `-c <不存在的目录>` **不报错**，只会静默
  回落到用户 home（实测 `pwd` 是 `/home/<user>`），而插件把请求的路径当作实际 cwd 报回去。
  现在先验证目录存在，否则明确报 `no such directory: <path>`。
- **关闭会话不幂等**：会话已经不在（或服务端已自行退出）时，`shell_close` 抛 tmux 原始错误、
  HTTP `/kill` 返回 500。面板列表稍旧时用户点 ✕ 就会撞上。现在关闭是幂等的，返回
  `closed:false, reason:'not-found'`，HTTP 仍为 200。
- **HTTP 错误码分不清「调用方写错」与「插件坏了」**：非法 JSON 请求体、缺少 `name` 都返回 500。
  现在统一映射：参数类错误 400，其余 500。

**测试**

- 新增 `npm run test:edge` 与 `npm run test:client`，CI 分别覆盖；`npm test` 一次跑完两者。
- `npm run smoke` 新增 4 组生命周期断言：harnessPid 必须落在本进程祖先链上、pid 文件指向别的
  harness 时会话必须存活、看门狗被杀后必须自愈重布防，以及两条防回归的静态断言
  （守卫排除自身、存活判定有容错）。

## 0.1.0 — 首次发布

**持久化终端**

- 基于私有 tmux socket（默认 `-L dsh-agent`）提供**跨对话存活**的持久 shell：会话由宿主进程
  持有，不属于任何一次对话，新开对话、切会话与**同进程热重载**都不会丢。
- 服务端配置通过 `-f` 在**启动时**写入：`history-limit`、`default-terminal`、关闭
  status / mouse、`escape-time`，避免事后 `set-option` 无法生效的坑。

**9 个模型工具**

- `shell_open` / `shell_send` / `shell_read` / `shell_history` / `shell_list` / `shell_resize` /
  `shell_rename` / `shell_close` / `shell_diagnose`。
- `shell_send` 同时支持一次性输入整条命令与「按键 + 文本 + 按键」的仿真序列
  （`preKeys` / `text` / `keys`），因此 vim 编辑、多行文本、`Ctrl-C` 打断都能在一次调用里完成。
- 输出稳定性检测：`shell_send` 默认等待画面稳定后再返回，避免读到半截输出。

**WebUI 悬浮面板**

- `shell.overlay` 悬浮面板，可拖动、八向缩放、位置与尺寸持久化，支持 256 色。
- 每个按键**实时透传**到 shell，不做缓冲区；配合输入法（IME）状态机正确处理中文上屏。
- 锁定按钮防止误触；失焦自动重新锁定；多 shell 切换（下拉选择）、新建 / 重命名 / 结束 / 最小化。
- 历史回看（`更多历史` 可扩到 5000 行）并带 pinned 感知的自动滚动；主动推送按钮可把当前画面推给模型。

**安全与生命周期**

- 危险命令护栏（默认开启）：作为**启发式减速带**拦截 `rm -rf /`、`mkfs`、`dd of=/dev/*`、
  `--no-preserve-root` 一类模式；明确说明它**不是沙箱**。
- 低权限模式：在 `workspace-write` 等受限模式下会明确报错，建议以 `danger-full-access` 运行。
- 孤儿 tmux 治理：tmux server 会 setsid 脱离宿主，因此额外拉起 detached watchdog 轮询宿主 pid，
  宿主消失即 `kill-server`；watchdog 支持被新宿主**收养**，同进程热重载不会杀掉用户正在用的 shell。

**解耦说明**

- 插件位于 **host 平面**（profile bundle），UI 注册在 `shell.overlay`（root scope），数据走同源
  HTTP。因此 shell 的生命周期与对话解耦：对话结束、插件重载都不影响正在运行的 shell。

**配置与测试**

- `extendedKeys`（默认 `false`）：置 `true` 时服务端启动配置会多一行
  `set -g extended-keys on`，TUI 程序（pi、codex 等）才能收到 `Shift+Enter` 这类带修饰键的按键。
  默认关闭 —— 该选项需要 tmux ≥ 3.2，且写在 `-f` 启动配置里，老版本 tmux 遇到未知选项会导致
  服务端起不来。已在 tmux 3.6b 实测开启后建会话、按键投递、会话存活均正常。
- `npm run smoke`：对**真实打包产物**做端到端冒烟 —— 自行 `npm pack`、解包、只链宿主 peer、
  用假 `ctx` 调 `apply()`，再同时经**工具路径**与**HTTP 路径**在私有 socket 的真 tmux 上建会话 /
  发按键 / 读屏 / 读历史 / 改名 / 缩放 / 关闭。CI 有独立 job 跑它。
- 面板指标行显示 **`v<版本> · <构建号>`**（如 `v0.1.0 · c11`），报障时直接报这一行即可定位版本。
- `npm run release:check`：机械校验**版本号 ⟷ CHANGELOG ⟷ 面板版本戳记**三者一致、`files`
  白名单覆盖运行期文件、入口可达、客户端仍是 classic script、源码未泄漏开发机路径或凭据；
  `npm publish` 前由 `prepublishOnly` 自动执行。
