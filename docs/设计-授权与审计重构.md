## 0. 目标收敛（维护者 2026-09-14 决定，最高优先，其余让位）

**只保证两件事**：

| 目标 | 能承诺 | 不能承诺（同用户模型的天花板） |
|---|---|---|
| **G1 必须人类授权** | 插件通道的授权只能由人类交互产生（AI 只能"请求"）；**每次授权/撤销事件都进不可篡改审计** → 伪造**必留痕、可发现** | 凭证对同用户 agent 可读 ⇒ 做不到"伪造不可能" |
| **G2 可审计 + 审计不可篡改** | 输入 + 输出 + 授权事件全部留痕；**篡改必可检测**（哈希链 + 外部见证） | 无 root 时做不到"物理改不了"；`chattr +a`（A 级）才能升级为**不可篡改** |

**合起来的保证**：AI **不能"悄悄"越权** —— 要么没授权可用，要么用了必留痕。

**维护者明确否决（不做）**：内存权威防自授、特权 sink 迁移、防 ptrace、防原生 bash 直连、跨平台适配。
理由（维护者判断，技术校准见 §8）：AI 一旦拿到 shell（含 DSH 自带 bash 工具），同用户模型下
"拦不住"是既定事实；**与其追一个不存在的边界，不如保证"授权必须来自人类 + 一切留痕不可抵赖"**。

## 1. 两个缺陷的实测确认（先立证据，再谈方案）

### 1.1 状态文件对 agent 完全可写（"自授"路径成立）

```
$ ls -la ~/.dsh/agent-shell
-rw------- Kal1 Kal1  consent.json          ← 授权表，可写
-rw------- Kal1 Kal1  sessions.json         ← 归属表，可写
-rw------- Kal1 Kal1  audit-2026-09-14.jsonl ← 审计，可写
drwx------ Kal1 Kal1  .                     ← 目录可写（可整体替换 consent.json）
```

`consent.json` 的语义是"键 → 授权信息"的字典。原生 bash 工具（不受插件护栏约束）可以直接写入
`{"<自己的会话 id>": {"scope":"full"}}`，宿主重启后 `index.js:917` 的启动合并
（`state.consent = { ...await readConsent(), ...state.consent }`）会把它当作已授权读回。
**agent 因此可以给自己发权限，且不经过任何人类确认。**

### 1.2 更根本：插件 tmux socket 可被原生 bash 直连（绕过整个插件）

```
$ ls -la /tmp/tmux-1000/dsh-agent
srwxrwx--- Kal1 Kal1   dsh-agent

$ tmux -L dsh-agent list-sessions -F '#{session_name}'   # 实测成功，退出码 0
```

socket 权限是"同用户可读写"。**原生 bash 可以直接 `tmux -L dsh-agent send-keys/kill-session/…`，
完全绕过插件工具、授权门与输入审计。** 这比改 `consent.json` 更直接 —— 除非收紧 socket 权限或
引入权限差，否则"插件授权门"在平台层面本就不是边界。

### 1.3 control-mode 命令存在未转义插值（注入面）

`lib/tmux.js` 的 control 路径把命令拼成**一行字符串**写进 tmux stdin，其中会话名是**直接插值**的：

```js
await this.control.command(`has-session -t ${name}`, …)                        // 未 quote
await this.control.command(`display-message -p -t ${name} ${tmuxQuote(FMT)}`)  // name 未 quote
```

`name` 来自工具入参 `session`（模型可控）。`session: "x; display-message -p INJECTED"` 这类取值会
被 tmux 当作**两条命令**执行。argv 路径（`run(argv)` 经 spawn 传参）没有这个问题：参数分离，
`;` 不构成 tmux 命令分隔。

### 1.4 普通用户无法 `chattr`（决定阶段 1 的落地形态）

```
$ chattr +a .chattr-probe
chattr: Operation not permitted while setting flags on .chattr-probe
```

`immutable`/`append-only` 需要 `CAP_LINUX_IMMUTABLE`（即 root）。**"日志加 chattr +a"必须包含
一次性 root 安装步骤，否则这条措施在该部署里等于没写。** WSL 的根分区是 ext4，能力上支持，
差的只是权限。

**结论**：方案的两个方向（权限不可改、可审计）都成立，但"独占 sink / chattr"必须显式依赖特权，
不能默认普通用户能实现。下面的修订方案据此重新定级。

## 2. 对原方案的审查

### 2.1 认可的部分

| 原方案 | 评价 |
|---|---|
| 先做阶段 0（堵绕过）再做 1/2 | **正确**。权限锁与审计在"能绕过"的前提下没有意义 |
| 权限/审计迁出 agent 可写区 | **方向正确**，但需特权支撑（见 1.4） |
| 删除 `pure.mjs` 里拦状态目录/sudo 的黑名单正则 | **正确**。见 2.2 |
| 不新造审计平面，只把已有 `pipe-pane` 正规化 | **正确**。现有输出流水覆盖面比想象中好（见 2.4） |
| 明确列出"不做"（eBPF / 意图对账 / 真沙箱） | **基本正确**，但与"加入多平台适配"冲突，见 2.5 |

### 2.2 黑名单正则必须删（它们提供的是虚假安全感）

`pure.mjs` 现有 4 条规则专门防"删/改插件状态目录"（`rm … agent-shell`、`> … audit-YYYY-MM-DD`、
`find … -delete`、`rm -rf ~/.dsh`）。问题：

* **挡不住**：正则只作用于插件自己的 `shell_run/shell_send`；原生 bash 工具与任何拼接/变量/脚本
  都不经过它。它们是"用文本匹配防文件系统操作"，本质无效。
* **会误伤**：正常命令里出现 `.dsh`、`agent-shell`、`audit-2026-…` 字样即被拦。
* 删除后保留真正的危险命令规则（`rm -rf /`、`mkfs`、`dd of=/dev/*` 等）——那些是**防手滑**，
  定位如实写在文档里即可。

### 2.3 "control-mode 默认关闭"过重（应该修插值，而不是砍掉性能）

control 路径的收益是实测的（3–5ms vs ~100ms/次）。真正的漏洞是**未转义插值**，不是 control 本身。
修订为：

* **阶段 0 主路径**：所有 control 命令改为**参数化构造** —— 会话名走白名单校验
  （`^[A-Za-z0-9_-]+$`，插件生成的 id 本来就满足）或统一转义层；任何插值点都必须过构造器。
* **保留兜底开关** `useControlMode: false`（全走 argv），给保守部署。
* 加**注入回归测试**：`a; display-message -p X`、`a$(id)`、反引号、换行、`\;` 等样本必须被拒
  或按字面处理（当前无此测试）。

### 2.4 "pipe-pane 流水"的真实覆盖面（比原方案说的更好，也更差）

* **输出面是全覆盖的**：`pipe-pane` 是**会话属性**，只要会话在插件列表里，任何来源的按键
  （包括 1.2 的原生 bash 直连）产生的输出都会进流水 —— 包括"绕过者干了什么"。
* **输入面只覆盖插件入口**：直连 tmux 发出的输入不经过 `shell_send`/`/keys`，因此**记不到"谁发的"**；
  直连 tmux 新建的**会话**完全不在插件列表，无任何流水。
* 结论：输出轴可以当"不能撒谎的现场"，输入轴只能标注"插件侧发起了什么"。这个不对称必须写进文档，
  不能含糊成"全链路可审计"。

### 2.5 "跨平台全部不做"与你的要求冲突

你提出"加入多平台适配"，原方案却把跨平台整体划到不做。修订为**最小多平台集**（见 §4）：
路径解析、哈希链纯 JS 实现、特权措施按平台降级标注；不做的是"每平台的等价防篡改机制"。

## 3. 修订后的三阶段方案

### 阶段 0 的收益与代价（维护者问询，先算清再动手）

**定位**：阶段 0 不是"锁"本身，而是**防止绕过锁的通道**。阶段 1 把状态文件锁住之后，注入是
**唯一还能以宿主身份写状态文件的路径**（control 命令 → tmux → `pipe-pane`/`run-shell` 由 tmux
server 执行 shell）。因此"不修则白锁"成立，它保护的是阶段 1 的有效性。

**收益**

| 收益 | 攻击样本 | 作用 |
|---|---|---|
| 堵住经 tmux 的任意命令执行 | `session: "x; pipe-pane -t dsh-mine -o 'cat > …/consent.json'"` | **关键**：阶段 1 文件锁的唯一绕过通道 |
| 堵住跨会话横向移动 | `session: "dsh-mine; send-keys -t dsh-victim 'evil' Enter"` | per-conversation 授权被绕过（操作别人的会话） |
| 堵住 DoS | `session: "x; kill-server"` | 服务端被毁 → 审计与权限一并下线 |
| `requireConsent` 不可热改 | `curl -X POST …/settings -d '{"patch":{"requireConsent":false}}'` | 切断"agent 立即关掉授权门"（HTTP 无鉴权，本机 curl 可达） |
| 删 4 条状态目录黑名单 | — | 去掉虚假安全感与误伤（挡不住原生 bash 的拼接/变量/脚本） |

> **限度**：`requireConsent` 不可热改 **≠ 不可改**。agent 仍可改配置文件、重启后生效。要真锁住，
> 配置本身也要进阶段 1 的权威（内存 + 哈希校验）或走 A 级 `chattr`。

**代价（两条路径二选一）**

| | 路径 A：默认关闭 control（原方案） | 路径 B：保留 control + 修插值（**建议**） |
|---|---|---|
| 性能 | 每次操作 `~1ms` → `~100ms`（**约 40×**）：面板逐键每键 +100ms、`/screen` 每次 +100ms、每次工具调用 +100ms | **零损失**（仍 ~1ms 管道） |
| 开发量 | 小（换成 argv，注入面一次性归零） | 中：8 个 `control.command` 调用点参数化 + 会话名白名单 + 注入回归测试 |
| 残余风险 | argv 传参天然分离，基本无注入面 | 怕遗漏插值点 → 加**静态检查**（`control.command` 必须过构造器，机制同 dev-sync 的导入校验） |
| 附带 | — | 留 `useControlMode:false` 兜底开关 |

**结论**：阶段 0 值得先做，但**只做阶段 0 不够**（"改文件自授"仍成立）；本轮目标是
**阶段 0a + 阶段 1a 的最小闭环**。

### 本轮最小闭环（~~第一优先~~ → **已被维护者否决，见 §0 与 §8**）

> 下表的"内存权威"曾被我列为核心，维护者指出：同用户模型下 AI 拿到 shell 后可通过调试手段
> 读取/修改内存，且 DSH 自带 bash 工具本就能做到 —— 因此"内存权威"不作为安全边界。
> 保留部分仅剩：**重启不自动信任磁盘授权**（人类授权有时效性，挡"改文件+重启"这条零门槛路）。

```
自授权不可篡改 = 重启不信任磁盘授权（保留，抬高成本）
              + 安全配置不可热改            ← 杀死"立即关掉授权门"
              + 插值参数化(阶段 0a)         ← 保证未授权会话不能靠 session 注入取得效果
审计不可篡改   = O_APPEND 追加写
              + 哈希链(prevHash, 纯 JS)     ← 断链/回退可检测
              + 链头外部见证(watchdog)      ← 防整体替换
              + [可选 A 级 chattr +a]       ← 一次性 root，内核级只追加
```

**同用户模型的天花板（必须写进文档）**：无权限差时只能做到「**阻止自授路径 + 篡改可检测**」；
要做到「**阻止篡改**」必须 A 级（一次性 root `chattr +a`）或 B 级（独立用户/容器）。

### 设计原则：授权层与使用层分离（回答"AI 改授权表算不算用户授权"）

**问题**（维护者提出）：用户既然授权了"完全控制 shell"，AI 修改授权文件是否也算用户授权的行为？

**结论：不能默认这样认为。** 授权是「用户 → AI」的**有向**约定；AI 能写授权表就等于
"自己给自己发授权"，授权者与被授权者合一，约束消失（self-authorization）。
类比：给员工全楼门禁卡（使用授权）≠ 允许他改门禁系统里自己的权限记录（授权层）。

破坏面（都不是理论危害）：

| 破坏 | 后果 |
|---|---|
| 撤销失效 | 用户点「完全禁止/撤销」后 AI 一条命令恢复 → 撤销只对老实 AI 有效 |
| 审计失效 | 能改/删审计 → 事后无法追责；审计的全部价值在可信 |
| 粒度击穿 | 授权是**按对话**给的；AI 写通配授权 → 所有未来对话永久免确认，**超出被授权范围** |

**落地原则**：

| 层 | 内容 | 允许的通道 |
|---|---|---|
| 使用层（use） | 执行命令、开关 shell、读写屏幕 | AI + 人类（受授权门约束） |
| 授权层（meta） | grant / revoke / 改安全配置 / 删改审计 | **仅人类**（面板 / 人工 CLI）；AI 只能"请求"（触发询问），不能写入 |

**显式放权选项**：若确实要让 AI 自己管权限（无人值守），提供默认关闭的开关
`allowAiSelfGrant: false`；**打开该开关本身必须人类操作 + 记审计**。此时才构成"用户授权的行为"。

**结论**：是否算用户授权，取决于用户是否**显式授予**该权利；默认不授予 —— "完全控制"约束的是
**在授权范围内做什么**，而不是**授权范围由谁定义**。

### ⚠️ 实测发现（2026-09-14）：agent 可直接冒充「人类面板」调用授权 API

对"授权层只接受人类通道"的致命前提做了实测：

| 探测 | 结果 |
|---|---|
| 无凭证 POST `/plugins/shell/consent` | `403 browser session is not authenticated`（平台层**有**会话鉴权） |
| agent 读 `~/dsh-web-url.txt`（**644**）/ `~/dsh-web.log`（0600）取 token | 可读（同用户） |
| 用该 token 换 cookie 后 POST 授权端点 | `400 action must be …` → **到达业务逻辑**（非 403） |

**即：agent 读一次 token 文件即可冒充人类面板执行 `{"action":"set","actor":"*"}` —— 给所有对话开
完全控制，立即生效、无需重启。** 比"改 consent.json"更直接。因此：

* "HTTP 就是人类通道"这个假设**不成立**；凭证保密性 = 该通道的全部安全性。
* 附带部署卫生问题（非插件 bug）：`~/dsh-web-url.txt` 是 644 且持有**整个 DSH web** 的凭证，
  建议删除或改 600，不把带 token 的 URL 落盘。

**阶段 1 必须补的选项**（三选一或组合）：

| 方案 | 机制 | 级别 |
|---|---|---|
| (a) 凭证不可读 | 特权/独立用户持有；或浏览器专属 cookie 且服务端不提供 token→cookie 兑换 | A/B 级 |
| (b) **改用 DSH 平台人类交互** | 授权只能经 `userQuestions` 弹窗产生（agent 无法代答）；HTTP 授予降级为"提议" | 平台级，**推荐** |
| (c) 诚实降级 | 承认可伪造，只保证审计留痕 + 可检测 | C 级，当前默认 |

**建议**：(b) 作为授权产生的唯一通道 + (c) 兜底；(a) 若维护者愿意引入一次性 root 步骤再叠加。
面板的"主动授予"（§1.5）据此改为**面板发起提议 → 用户在对话里确认**，既满足"可主动授予"，
又不依赖可被伪造的凭证。

### 路径决策（维护者 2026-09-14）

* 阶段 0 走**路径 B**：保留 control-mode，修插值（零性能代价），并按 §3 的静态检查兜底；
  留 `useControlMode: false` 作为可选兜底开关。
* 待确认：安全相关配置（`requireConsent` / `auditDir` / `guard`）改动需重启是否接受；
  是否引入一次性 root `chattr +a`（A 级）；"按对话主动授予"的会话列表来源。



### 阶段 0 —— 地基：先把能绕过的路堵上（不修则白锁）

| 编号 | 改动 | 验证 | 取舍 |
|---|---|---|---|
| 0.1 | control 命令**参数化/转义层**：会话名白名单 + 所有插值点过构造器 | 注入样本回归测试（见 2.3） | 保住 control 性能；多一层构造代码 |
| 0.2 | `useControlMode`（默认开，可关为全 argv） | 关掉后功能全绿 + 性能基线记录 | 保守部署的兜底 |
| 0.3 | `requireConsent`、`auditDir`、`guard` 等安全相关配置**不可热改**（重启生效），改配置本身入审计 | 设置页保存后返回"需重启"；审计有 `event:config` | 少数场景要多一次重启 |

> 关于 socket：把 `/tmp/tmux-1000/dsh-agent` 权限从 `rwxrwx---` 收紧没有意义（同用户本来就
> 拥有该目录）。真正的隔离只能靠**不同用户/容器**（见阶段 1 的降级分级），或接受 0.4 的诚实声明。

### 阶段 1 —— 权限不可改 + 可主动授予

#### 1.1 授权权威移入"内存"，重启 fail-closed（不依赖特权的核心改动）

* 运行期唯一权威 = 宿主进程内存 `state.consent`（已是），**取消"启动时从磁盘合并授权"**
  （`index.js:917` 改为：磁盘只用于展示/取证，不作为放行依据）。
* 重启后授权默认失效，需重新确认（或由人工在面板一键重授）。**这直接杀死"改文件自授"路径**：
  没有可写的放行依据。
* 代价：宿主重启后每个活跃对话要重新授权一次。可用"面板主动授予"（1.5）缓解。

#### 1.2 持久化与防篡改分级（按可用特权选择，文档如实标注）

| 级别 | 条件 | 能力 | 诚实标注 |
|---|---|---|---|
| A | 安装时 root 执行一次 `chattr +a` 审计/授权目录 | 追加不可改、删除不可为（同用户也不行） | "已启用内核级只追加" |
| B | 独立用户/容器运行宿主 | agent 无法读写宿主用户目录 | "已启用用户隔离" |
| C | 无特权（当前默认） | 仅**可检测**：哈希链 + 拓扑快照比对 | "可检测篡改，不能阻止篡改" |

* 无论哪级，**审计写入统一 `O_APPEND`**（现为 `appendFile`，已是追加；需固定 `flags:'a'` 并注明）。
* **哈希链**：每条记录携带 `prevHash`（内存维护链头，纯 JS SHA-256，跨平台）。启动时校验；
  断链/回退即报"审计可能被篡改"（面板 + `shell_audit` 顶部）。
* **外部见证**（可选，级别 C 的补强）：watchdog 定期把链头 + 条数写入它的独立存储（与主审计
  不同 inode）；篡改主日志会造成"链头对不上"。

#### 1.3 删除 `pure.mjs` 状态目录黑名单（4 条），保留危险命令启发式

* 见 2.2。同时把 `guard` 的定位在文档和工具描述里统一为"防手滑的启发式减速带"。

#### 1.4 子代理继承改为"受限继承"

现状：子代理无人类可问 → 只要进程内有人类授权过就继承 **full**。
修订：继承父级的 **scope 最小值**（父为只读则子也只读），并记录 `inheritedFrom`；
新增配置 `inheritConsent: 'scoped' | 'full' | 'deny'`（默认 `scoped`）。

#### 1.5 面板/HTTP 主动授予任意对话（你的点一）

新增 `POST /plugins/shell/consent`
```jsonc
{ "action": "grant-actor", "actor": "<会话 id>", "scope": "read|full|deny", "ttlSeconds": 600|null }
{ "action": "revoke-actor", "actor": "…" }
```
**难点是"面板怎么知道有哪些对话"**，两个来源（都要）：
1. 宿主已有的会话目录服务（DSH 的 session 列表）→ 面板列出"当前活跃对话"，逐条授予；
2. 已授权条目 + 审计里出现过的 actor（历史），可续期/改档。
UI：0.2.0 重绘的「权限控制」浮层增加"按对话"分区（档位 × 有效期 × 单条撤销），
与现有"所有对话（通配）"并列。授予动作 `source:'panel'`、审计记 `decision:'human-panel'`。

#### 1.6 授权事件全部进审计（含授予来源）

`grant`/`revoke`/`expire`/`inherit`/`deny` 每条带 `source`（panel/tool）、`actor`、`scope`、`ttl`、
`decision`。**撤销与授予同样是审计事件**，不能只记"用"不记"授权"。

### 阶段 2 —— 可审计：把现成流水正规化

## 4. 多平台适配（最小集，替换原方案的"全部不做"）

| 关注点 | Linux | macOS | Windows / WSL |
|---|---|---|---|
| 状态目录 | `${DSH_HOME:-~/.dsh}/agent-shell`（现状） | 同 | WSL 同 Linux；原生 Windows 用 `%USERPROFILE%\.dsh\agent-shell` |
| 追加写 | `O_APPEND` | 同 | 同（Node 统一） |
| 防篡改特权 | `chattr +a`（root 一次） | `chflags`（受限，多为 no-op） | NTFS ACL 只读 + 审计（尽力而为，标注"不可靠"） |
| 哈希链 | 纯 JS，跨平台一致 | 同 | 同 |
| 时间 | 存储 UTC，展示本地 | 同 | 同 |
| 不做的 | 每平台"等价防篡改"、eBPF、网络外发 SIEM | 同 | 同 |

结论：**跨平台做"能一致的部分"（路径/哈希链/时间/环境变量），特权级只承诺 Linux（可选 root），
其余平台如实标注为 C 级（可检测）**。

1. **重启后授权是否 fail-closed**？我建议**是**（这是杀死"改文件自授"的关键，代价是重启后要重授）。

## 8. 技术校准（维护者判断的精确化，2026-09-14）

维护者的结论"拦不住"成立，但机制需要校准，避免设计建立在错误假设上：

| 攻击路径 | 本机实测/内核配置 | 结论 |
|---|---|---|
| 直接 ptrace 宿主内存 | `yama/ptrace_scope = 1` → 同用户**不能** attach 非子进程 | 这条在当前内核配置下不通用（除非宿主是其子进程，或 sudo 可用） |
| **改文件 + 触发重启** | 状态文件同用户可写；宿主由守护脚本拉起 | **零门槛，成立** —— 这是"重启不自动信任磁盘授权"要挡的路 |
| **原生 bash 本就有 shell** | DSH bash 工具以同用户运行 | **成立且不可挡** —— 插件授权门约束的是"插件这条通道"，不是"AI 能否拿到 shell" |
| 用读到的 web token 冒充人类面板 | 实测：`~/dsh-web-url.txt`(644) 可读 → 换 cookie → POST `/consent` 到达业务逻辑 | **成立** —— G1 因此只能承诺"伪造必留痕、可发现" |

推论：把力气放在**审计完整性**（G2）与**授权入口收敛**（G1）上，而不是"让 AI 改不了"。

## 9. 收敛后的实施范围

**做（按优先级）**

1. **审计完整性（G2 核心）**
   - `O_APPEND` 追加写；每条记录带 `prevHash`（内存维护链头，纯 JS SHA-256）
   - **授权事件全部入链**：`grant`/`revoke`/`expire`/`inherit`/`deny` + `source`(panel/tool) + `channel`
   - **篡改显式可见**：启动与查询时校验链；断链/回退 → 面板红条 + `shell_audit` 顶部 + 日志（绝不静默）
   - **外部见证**：链头 + 条数写第二处（watchdog 独立文件；评估 DSH 会话日志作第二见证）
   - 输出轴纳入：`pipe-pane` + 会话边界 + 密码脱敏；如实标注"输入轴只覆盖插件入口"
2. **授权入口收敛（G1）**
   - 授权只能由人类交互产生；面板"主动授予"= 面板提议 → 用户在对话里确认
   - 所有授权事件入审计（含来源与通道）
3. **便宜小项**
   - 重启不自动信任磁盘授权（授权需重新人类确认）
   - 阶段 0a 注入参数化 + 注入回归测试（保证授权判定不被 `session` 参数绕过）
   - 安全配置不可热改（`requireConsent`/`auditDir`/`guard`）
   - 删除 `pure.mjs` 4 条状态目录黑名单
4. **可选 A 级**：`install-deps.sh --audit-lock` 做一次性 `sudo chattr +a`（内核级不可篡改）

**不做**：内存权威、特权 sink、防 ptrace、防原生 bash 直连、跨平台适配、eBPF、意图对账、真沙箱、审计外发。

**待维护者拍板**：是否引入 A 级 root 步骤（决定"不可篡改" vs "篡改必可检测"）。
建议：代码两条都支持，`chattr` 做成可选安装项，不阻塞开发。
